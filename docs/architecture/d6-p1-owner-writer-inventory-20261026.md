## Data ownership and evidence classification

“Authoritative” below identifies the implementation's owning data, not a claim that the current filesystem is qualified, immutable or authorized for acquisition.

| Data | Existing owner / source contract | Classification and limit |
| --- | --- | --- |
| UIB extension package identity/capabilities | `packages/platform-core/src/manifest.ts`, `manifest-discovery.ts`; owning package's `.manifest.json` | Authoritative declaration when validated and uniquely resolved. | Canonical Card Definition/export | `src/server/component-registry.ts` consumes explicit `ui.component.json`, `package.json` and runtime module/export declarations | Explicit canonical Definition/package metadata is the relevant identity source. | App package activation | `src/server/packages.ts`, `app-manifests.ts`: permanent Application's declaration, enabled/version/resolution fields; registry discovery also consults app/platform dependencies and settings | Activation identity is separate from installed identity. ## Foundation ordering

Reuse the existing single canonical `platformComponentsRoot` graph, identity `visual-runtime-graph-v1`, then declared owner role locks. `withApplicationMutation`'s `_root` argument does not create per-App graph authority. R1 refuse mode is explicit on each graph/role/root/list/read edge, not ambient. Existing trusted callbacks, package plain-file IO and subprocess writers do not become constrained merely because another caller holds this graph.

For a mutable-graph solution, **every supported writer's first relevant byte/membership mutation through final publication must participate**, including delegated helpers and subprocess lifetime. This is not demonstrated today. Wrapping only the read, final metadata save, installer rename or activation update is insufficient. Holding a graph lock across arbitrary external build actors is not an existing guarantee.
