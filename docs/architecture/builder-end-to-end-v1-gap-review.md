# Builder End-to-End V1 — Integration Gap Review

Review date: 2026-10-13 (America/New_York). Baseline: `85eaf81bcf68d948dd9a3a59b35d2ed3c060eed5`; working tree clean before this audit. Scope: review and planning only. Companion documents: [plan](builder-end-to-end-v1-implementation-plan.md), [checklist](builder-end-to-end-v1-acceptance-checklist.md), [inventory](builder-end-to-end-v1-review-inventory.md).

## Executive summary

The repository contains substantial accepted engines and editors, but does not yet provide the required UI-only development Application journey. The current Builder stacks composition, visual editing, and legacy Page source editing; generic artifact editing and automation management have separate entry points. Existing tests establish subsystem behavior, not creation of a complete new protected Application through one Builder.

The five largest remaining gaps are:

1. **New-Application authority and runtime onboarding.** Development management explicitly restricts Application access to the identity fixture. The Standard template has no protected data proxy configuration, and its development API is a health stub. Reference launchers provision data/authority programmatically.
2. **One focused artifact workspace.** No common open-artifact tab coordinator connects Pages, Shells, shared Components/Forms, Datasets, automation and Menus while preserving independent working copies.
3. **Consistent editing lifecycle.** A strong generic working-copy implementation exists, but visual, composition and automation editors use separate save/state handling. Per-artifact logical Undo/Redo is missing from these inspected paths. Existing repair saves deliberately allow invalid authoritative source, contrary to the proposed normal autosave policy.
4. **UI authoring of data and behavior.** Forms start from pasted published schema JSON; automation creation asks for raw identities and action configuration remains JSON. Events, slots, visibility and data sources are substantially metadata-authored. Generic Form/Route proof editors do not fill these Visual Artifact gaps.
5. **Safe focused tests and aggregated diagnostics.** Actual visual rendering is reusable, but preview services point to the ordinary session data proxy. Application-wide validation is fragmented and composition validation throws rather than returning a complete navigable problem list.

Recommendation: retain accepted source formats, ownership and engines; add adapters, workspace coordination, narrowly scoped development host integration, and the missing authoring controls. Total effort is **Large**, with data/authority integration the highest uncertainty. Do not claim V1 readiness from the 64 focused tests passed in this audit.

## Architectural inconsistencies and reconciliation

### Save policy is a real boundary, not a UI label

Generic Artifact Foundation and VisualArtifactService intentionally permit malformed/invalid source for repair. `artifact-editor.test.ts` verifies this; the older readiness guide explicitly promises it. AutomationStore instead parses and validates before saving. Visual saves are sequential per role and can partially succeed; generic Foundation supplies bundle transaction/recovery semantics for its own format. Do not imply all editors already have equivalent persistence.

Normal Builder autosave should stage changes locally and validate the complete intended bundle through authoritative subsystem validation before writing. Keep engine repair behavior and a clearly explicit source-repair path. A client-only validity check is insufficient to prevent a stale or externally changed candidate from reaching authoritative source. Any added server candidate validation/commit adapter must recheck its concurrency token under the existing service lock. Do not convert Visual bundles into generic artifact.json bundles merely to reuse the client lifecycle.

### Artifact formats and identity

Generic `form`/`route`/`routeGroup` proof artifacts coexist with Visual Form-capable Components and Page-owned `routeId`/`route`. Automation has its own accepted Platform source format. These are distinct consumers, not evidence that one editor can directly edit every format. Retain generic proofs for their supported sources, but route the V1 journey to accepted Visual Components and composition Page routes. A Form tab is a capability-specific view of the same permanent Platform Component identity. A Page's primary Route must not become a second editable Route truth.

Tab keys should qualify stable artifact identity with owner/type; package identity remains package-owned. Opaque generic locators and relative Visual/automation locators are transport handles, not authorization or permanent identities. Malformed artifacts without a recoverable ID need a scoped repair locator key; never invent a permanent ID. Shared Platform definitions opened from two Applications require the same owner-qualified identity and fresh access checks.

### Validation and references

Structured Foundation diagnostics already support severity/code/identity/file/line/column/field/path. Visual diagnostics and automation strings have less location information; composition often throws the first error. Adapt results without copying rules. Add locations at the original validator where practical; otherwise navigate to the artifact and label location unavailable. Application aggregation must distinguish invalid saved source from local pending edits and enumerate reachable Platform dependencies without claiming authority over unrelated Applications. Definition changes must invalidate every affected open Application's dependency view.

`ArtifactEditorWorkspace` constructs its own Foundation service without a supplied reference resolver; outgoing references alone do not establish that all external targets exist. Reuse explicit Dataset applied-resource, Workflow and service catalogs/resolvers. Preserve the accepted difference between Visual named-path bindings and automation explicit JSON value bindings; controls must serialize each contract rather than invent a unified expression language.

### Runtime and authority

Visual preview already uses the actual renderer. Its services use the same ordinary protected session proxy as runtime; an iframe and fixture inputs do not isolate writes. Workflow failure may leave prior steps committed; afterCommit failure may report committed data. Test isolation cannot rely on rollback alone. Use disposable storage, applied schemas and scoped authority plus deterministic external-service substitutes.

Reference schema publication is Dataset infrastructure, distinct from Application Presentation Publish. Applying/connecting a development Dataset may require accepted schema publication/activation internally; this must not require publishing the Application. The offline migration adapter explicitly does not create/delete Datasets and requires stopped writers for supported migrations. Do not use it to pretend new live Dataset onboarding exists.

The current fixture restriction, separate management/applied-resource resolvers, absent Standard proxy wiring and host-owned service registration are blockers to the new-Application reference journey. Resolve them using existing development identity and trusted services. Production WP7 is not a prerequisite; trusted host service code remains engine/bootstrap work, while the developer selects approved services in Builder.

## Deferred scope and decisions

Preserve all work-package exclusions: production WP7/deployment, app-owned Components, full self-hosting, automatic Git commits/pushes, visual Git merge, advanced releases, shared asset libraries, template inheritance, workflow branching/queues/retries, realtime collaboration, generalized CMS, advanced theme designer and broad engine replacement/refactoring.

One product decision genuinely affects acceptance: **Does the no-manual-source criterion also exclude writing raw JSON/TypeScript in Builder's Source/metadata panels?** Recommended interpretation: yes for the primary reference journey; source panels remain repair/advanced tools. Pasting published schema/action JSON is therefore a gap, not successful no-code authoring. This review uses that stricter interpretation and does not ask for routine architectural choices already settled by accepted contracts.

Proposed development security provisioning policy requires architecture review before implementation: an authorized Platform Manager initiates new-app onboarding and an authorized security administrator assigns scoped roles through existing trusted activation; ordinary creators do not receive silent authority. This is a proposed reconciliation, not implemented or newly accepted policy.
