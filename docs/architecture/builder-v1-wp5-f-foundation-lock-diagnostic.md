## Foundation lifecycle and classification

`packages/artifacts/src/storage.ts:107–234` supplies the local queue and filesystem admission. The storage directory is `.uib/locks`; the filename remains SHA-256 of the caller's existing identity. Role-bundle callers canonicalize roots, directory and anchor through `realpath` and reject symlink/path/casing escapes (`role-bundle.ts:30–65`). Graph identity remains `visual-runtime-graph-v1`. Nothing in this investigation changes those identities or authorities.

1. `open(file,"wx")` exclusively creates a visible, initially empty file. This is ownership acquisition, but the PID is not yet published.
2. In a later async step, `handle.writeFile(String(process.pid))` publishes the owner text, then `handle.sync()` completes before the protected callback. The finally block closes the handle, then removes the lock. Visibility of the filename therefore precedes valid owner metadata; the source does not atomically publish a complete owner record.
3. A contender receiving `EEXIST` reads the text and converts it with `Number()`. Empty/whitespace becomes zero. A positive integer passes the syntactic check. There is **one initial read and up to three additional reads**, separated by existing 20-ms timers. This is not a guaranteed 60-ms wall-clock deadline: filesystem work, timers and scheduling can extend it.
4. If still invalid, the guard at `storage.ts:197–200` throws a generic incomplete-lock/operator-recovery error. It does not know a PID and does not probe liveness. `withArtifactLock` only repeats acquisition for `ArtifactBusyError`; this generic error escapes immediately, even if most of the existing five-second acquisition budget remains.
5. For a syntactically valid PID, `process.kill(pid,0)` probes liveness. A live PID leads to `ArtifactBusyError` and bounded acquisition waiting. Only `ESRCH` enters existing recovery: exclusive `.recovery` file, reread/compare owner, remove the dead-owner lock, then exclusive creation of the replacement. Other probe errors do not authorize removal. Journal recovery is separate, inside admitted role work; an incomplete owner prevents reaching it.

The guard safely refuses to steal an unknown owner's file, but its message does **not** reliably distinguish transient live publication from an abandoned empty file. It establishes unresolved metadata, not corruption or a proven need to repair the source journal. A failed write/sync normally enters the finally cleanup; abrupt process exit between creation and PID publication can leave an ownerless file that cannot be safely PID-recovered. Close/unlink failures or filesystem errors are further possible paths, not observed causes of the retained suite failures.

The per-module local queue serializes the same key within one module instance. Cancellation releases its queue slot only after its predecessor, preserving later ordering. It does not serialize other processes or distinct module instances. Cross-process contenders can observe the creation/publication window. A queued graph handoff's existing yield changes scheduling, not the requirement that PID publication follows exclusive creation. Abort is checked outside the metadata-read sequence and before entering work; it does not interrupt each owner reread. An unresolved-metadata error can therefore win over an abort during that sequence. This was reproduced without entry into protected work.

The PID-publication ordering and initial-plus-three guard predate D6: accepted HEAD contains them, and `storage-history.txt` identifies `bb7b2b6` (2026-10-15, accepted WP2). The D6 acquisition wrapper can propagate this pre-existing generic error without using the rest of its budget. That is a code-path fact, not proof of when the observed UI failure first began. PID reuse and partial-but-integer text are limitations of PID-only parsing; neither was observed here and neither is proposed as the suite cause.

## Diagnostic console collector correction

The preserved representative script runs native output redirection under Windows PowerShell 5.1 with `ErrorActionPreference=Stop`; a native stderr diagnostic becomes a terminating `NativeCommandError`. The child suite's complete JSON survived, but console collection and post-run script bookkeeping did not. The prior script/log/evidence are unchanged.

The new diagnostic-only `Invoke-NativeCapture.ps1` uses `System.Diagnostics.Process` with shell execution disabled, hidden window, and independent redirected stdout/stderr. Both streams are drained concurrently with `ReadToEndAsync`, preventing pipe deadlock. Stderr remains data. It records the native exit code and a completion/error record in finally, then returns a status object so the caller can preserve post-run evidence before deciding its own exit status. It does not convert a failing native process into a passing result. Output streams are preserved separately; exact cross-stream interleaving is not promised. Process-start/collector I/O failures are distinct from the native exit code. This helper is intended for trusted native executable paths/arguments; a future suite wrapper can call the existing Node/Vitest CLI directly rather than changing production test configuration.

Independent Windows PowerShell **5.1.26100.9711** verification runs only `collector-child.cjs`: 2000 stdout lines and 2000 stderr lines (over ordinary pipe buffer capacity), native exit **7**. `collector-verification.json` confirms post-run evidence collection was reached; `collector-content-audit.json` compares **every line** with expected bytes/content and confirms both complete streams, exit 7 and no collector error. The verifier itself succeeds because the expected failure was correctly retained. No UI or product regression suite was run to verify this diagnostic infrastructure.

## Smallest corrective proposal and review gate

The evidence supports correcting the **classification of unresolved publication metadata**, but does not establish the historical suite root cause. The smallest candidate for architecture review is an explicit unresolved-owner/publication state that remains fail-closed, leaves the file untouched and can participate in the existing bounded acquisition budget. At budget exhaustion, diagnostics must report unresolved metadata without claiming a proven dead/corrupt owner. A valid PID continues through existing liveness and recovery rules; source journals remain under their existing authority. Abort/deadline behavior within metadata reads must be explicit. This is a proposal only: it must not silently change permanently invalid locks into recoverable locks or weaken manual recovery requirements.

Atomically publishing a complete owner record is a broader alternative affecting creation/ownership guarantees; do not adopt a temp-file/link/rename scheme under diagnostic authorization. The architecture review should choose whether to preserve the existing publication protocol and refine transient/unresolved classification, or change publication itself. No increased timeout, broad retry, ownership stealing, lock deletion, graph identity change or journal bypass is recommended.

Required regression coverage after a separately approved design: live gated publisher beyond the short read window; publication between reads; abandoned empty and corrupt records; failed write/sync/close cleanup; valid live/dead/PID-reuse limits; cancellation/deadline before admission; local and cross-process handoff; canonical alias/case identity; journal recovery and original source validation; no callback replay or interruption after admission. An eventual historical-recurrence capture would additionally need lock identity/path, read bytes, creator/write/close ordering and owner liveness at the failing guard. Do not automatically launch another complete suite for that evidence.

**Stop for separate Foundation architecture review before implementing any publication/ownership/recovery or unresolved-state correction.** No implementation is authorized or performed here. D6 remains blocked by the preserved **491/501** complete UI result; successful probes and collector verification do not replace it.
