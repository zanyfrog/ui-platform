## Required capture/refusal contract — specification only

This describes the obligation for a future implementation. It is not an implemented API and does not amend accepted L1/L2/L3 behavior.

The source owner must resolve the original permanent Application UUID through the trusted registered owner, resolve the owner-qualified saved Page uniquely, and compare its complete five-role bytes/hash with the accepted request. The selected stable Card node must exist uniquely in that saved source via the existing hardened parser/validator, never editable drafts, DOM, focus labels or generated IDs. Preserve both the source binding and canonical implementation binding, including legitimate explicit absence of Definition revision.

The candidate must be bound to the exact original request/generation, trusted session/owner continuity, source/selection generations, canonical Page/node/hash and complete dependency evidence. Page, shared Component, package/Definition/export/activation, applicable theme and resource membership/bytes must be complete. Record exact content digests and authoritative revisions; package version strings and Page hashes alone do not close the dependency graph. Functions, styles, child content, assets and semantic dependencies must either be captured through supported contracts or cause refusal. No silent omission, execution fallback or default theme assumption is allowed.

One existing canonical graph acquisition must enclose discovery, capture and closure revalidation, with graph→role order and explicit recovery-free options on each Foundation edge. A reliable owner fence or immutable publication certificate must cover every required participant. Independently changing bytes cannot be certified solely by repeating a mutable read and observing the same hash. Missing/ambiguous membership or unqualified writer participation must refuse.

Immutable output must use server-owned sealed/copy-isolated bytes and an immutable metadata index consistent with accepted capture validation; freezing a wrapper around mutable buffers or returning filesystem paths/live resource URLs is insufficient. No credential, policy payload, lock owner, journal content or filesystem path may be exposed as a refusal or browser grant. Candidate creation does not authorize disclosure or rendering.

Cancellation must use the admitted bounded acquisition mechanism and reject publication after original session/owner/request generations become stale or superseded. Late owner results cannot revive a canceled capture. Revalidate source identities, all membership and digests, implementation activation and trusted authority immediately before candidate return; future disclosure requires independent original-authority reauthorization.

Required refusal distinctions include invalid/original-request mismatch, denied/unqualified authority, missing/duplicate/ambiguous identity or dependency, unsupported semantics/resources, changed/incomplete closure, busy/unresolved/unsafe/recovery-required admission, cancellation and stale/superseded generation. Internal exceptions must become structured, non-disclosing refusal results. R1's existing storage codes remain unchanged. No new runtime refusal type or availability branch was introduced here.
