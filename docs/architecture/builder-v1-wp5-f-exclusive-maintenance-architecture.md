## Boundary and operator authority

The boundary is **the normal Windows instance not running**, together with a trusted, deliberately minimal maintenance environment that has exclusive physical/local access to the identified volume. Its safety assumptions must be explicit: one authorized operator; trusted boot image and validation tools; no unapproved startup/repair scripts; no target drive sharing or second writable mount; no uncontrolled maintenance-shell consumer; and no normal-OS resume/relaunch until completion. This excludes normal process relaunch rather than repeatedly looking for its absence. It is an operational boundary, not an extra application lock.

Before any future transition, the operator must stop new ingress and use existing normal shutdown/drain paths for Platform/API, Builder/runtime previews, source watchers/compiler/CLI/test workers and all relevant user sessions/services. Known admitted operations must finish or preserve their existing recovery records. Do not forcibly kill an unidentified publisher to make a snapshot quiet. If graceful shutdown requires a forced termination, new journal state appears, the machine is hibernated/Fast Startup rather than fully shut down, or drain cannot be accounted for, stop for a separate decision. Full boot into the maintenance environment then establishes that no original OS process remains executing; final offline state must still detect any changed metadata or recovery artifacts.

Administrative/physical boot authority, target-volume access, any necessary local BitLocker unlock capability, and rights to read security descriptors and rename the exact object must be available. Required backup/audit privileges, including SACL visibility if needed, are prerequisites; no privilege escalation or security setting change is implicitly approved. The operator enters any unlock secret locally into a trusted tool, never into task logs or this chat. Do not disable encryption or Secure Boot merely to make recovery convenient. A boot-policy obstacle is a stop condition requiring a separate approved solution.

This proposal does not rely on the old owner's identity being inferred. Exclusion comes from a controlled environment in which that original OS cannot execute. A new operator/helper is explicitly the only permitted accessor, with an audit manifest and separate execution authorization. The `.recovery` guard is not used to confer that authority.

## Proposed quarantine and rollback mechanics

Use a reviewed native helper based on `SetFileInformationByHandle(FileRenameInfo)` with `FILE_RENAME_INFO.ReplaceIfExists = FALSE`. Microsoft documents that an occupied target then returns an error. Retaining the same source handle permits identity verification and rename without a close/reopen check-then-move gap. The API and its access requirements are documented, but **the helper, structure layout and behavior on this machine/environment have not been implemented or tested**. [FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info), [SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle).

The reviewed helper must open the existing exact file with `OPEN_EXISTING`, appropriate read/security/DELETE access and no sharing, reject reparse/multiple-link/identity changes, read final metadata through that same handle, and verify the same-parent destination on the same identified volume. Failure to obtain exclusive access is an abort, not permission to close somebody else's handle. No delete disposition, replacement flag, copy/delete fallback, delayed-reboot move, retry-to-force-access or directory-wide rename is allowed. The held handle is an additional object check; the offline boundary is what prevents another consumer acquiring the newly absent original pathname.

The only proposed transition is:

`<exact-key>.lock` → `<exact-key>.lock.quarantine-<approved-run-id>`

in the existing `.uib\locks` directory. Require a fresh fixed destination, native no-replace behavior and matching volume/file identity. On success, retain the original object as quarantine and record file ID, content/security checks, expected-path absence, native result and metadata changes. If the API result or interruption is ambiguous, inspect both exact names/file IDs while remaining offline; never blindly repeat a rename or boot normal Windows.

For validation, keep normal consumers excluded. Only the reviewed normal Foundation reader/helper may temporarily create its own PID lock at the now-free original pathname. It must complete normal read/recovery checks, compare all Component bytes/IDs and release its own lock before proceeding. It must not serve the application, run Component code or repair newly discovered journals under incidental authority. A new pending journal, unexpected hash or unknown lock stops the operation.

Rollback uses the same no-replace handle-based rename on the original quarantined object, **only after the approved reader has exited/released its own lock and the original pathname is absent**. An occupied original path, changed quarantine ID/bytes/security, source/journal mutation or inability to prove exclusion blocks automatic rollback. Keep the store offline for operator review; never delete/overwrite the new path to restore the old one. An empty original lock restores the prior fail-closed state, not a proven healthy source state. Retain the whole execution history; do not reset metadata to pretend quarantine never happened.

The no-replace flag addresses destination collision, the held handle addresses the source-object selection gap, and the maintained offline environment addresses concurrent/future consumer access. None substitutes for the other two. Power loss, an unexpected reboot, lost helper handle or unavailable independent evidence requires re-establishing the environment and reconciling both names/IDs before any normal service restart.
