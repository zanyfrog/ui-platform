## Implemented delegated-execution contract

WP6 uses the approved narrow declarative executable provider. Existing TypeScript/in-process Trigger handlers remain available only under ordinary current-User authority. A Service-mode registry row cannot run its registered handler. When the current actor is a Service, a nested inherit Trigger must itself be a verified published declarative program; arbitrary in-process TypeScript fails closed.

The application-owned Trigger Draft is published through Data Services `TriggerManager`/the versioned-definition registry. Its active definition has a permanent Trigger ID, Application ID, permanent initiating Dataset ID, phase, explicit execution identity, and v1 `serviceProgram`. The runtime registry row links the permanent ID and publication key but is not authority. The protected host re-reads the verified active publication, checks the row against it, and computes a canonical SHA-256 executable-content digest. The digest covers the full program and every execution-relevant identity: Trigger, Application, initiating Dataset, phase, Service, approval and capability. Display metadata and JSON formatting are excluded. Draft edits do not change the active digest; changed published behavior does; identical republished behavior restores it. Approval still must be current and exact. Service-mode `afterCommit` is rejected because its independent transaction would violate the v1 atomicity contract.

The JSON format is `{"format":"ui-platform.service-executable","version":1,"steps":[...]}`. V1 allows 1–16 ordered, bounded `read`, `count`, `exists`, `create`, `update` and `delete` steps, permanent Dataset/Field IDs, limited selection/row counts, restricted comparisons and Boolean conditions, scalar input/old/prior-step references, and only `concat`, `add` and `coalesce` transforms. Unknown fields/operators, scripts, imports, callbacks and forward step references fail validation. The trusted interpreter sees only a bounded DOE read/write port; it cannot receive ORM, raw I-AM, filesystem, an actor-switching API, or a general host-language function. The format and publication contract are also described in the Data Services `packages/trigger-manager/README.md`.

The host verifies the published executable and current `SecurityServiceUseApproval` before issuing a short-lived opaque Service actor lease. I-AM evaluates the Service's direct Permission Set assignments. The WP4 planner applies the approval ceiling to every delegated operation and Field use, and rechecks current approval and policy during DOE freshness checks. DOE retains WP5 Dataset/Field/row rules, final-write authorization, query restrictions, and joined transaction semantics. Nested Service transitions require a new approval check; nested verified inherit retains the current Service. The root User, prior actor, Service, approval, digest, publication version, capability, initiating resource, correlation and chain are recorded without record payloads. Audit distinguishes program completion from transaction commit/rollback. The delegated lease is invalid after execution. Outputs to the initiating caller contain no delegated records or step results; ordinary errors expose bounded codes.

UI Platform Trigger authoring accepts a `program.json` role with an explicit phase and compiles it to `service-program.json`. A Service-mode TypeScript source or `afterCommit` program fails validation. Ordinary TypeScript Trigger source remains supported and legacy definitions with no execution identity inherit the current actor. The trusted `publishServiceTriggerArtifact` bridge loads the committed application artifact, validates and compiles it, publishes its exact declarative program through Data Services `TriggerManager`, independently verifies the active definition, and creates the runtime registry index. The deployed host re-reads that verified publication; the caller never supplies a digest as proof. Neither artifact metadata nor a runtime row grants Service authority. A developer's draft edit does not change the active digest; publishing changed behavior requires a matching new WP3 approval.

The development host also exposes an internal, file-backed delegated job runner when the deployment supplies a protected queue directory. It is not an HTTP route. A root job is fixed by deployment to one Trigger and one Service. Its `System` actor records scheduler initiation; the current I-AM principal is the fixed Service and every operation still passes through DOE. A User-queued job records the initiating User. Queue files contain bounded input and references, never an actor lease, token, context or open transaction. Every resume/retry gets a fresh trusted context, verifies the current publication/digest, rechecks approval and assignment, and opens a new DOE transaction. A failed pre-execution check leaves intent queued for a later recheck. After execution starts, a failure marks the job indeterminate and blocks automatic replay because commit outcome may be unknown. Queue, denial, resume/retry, program and transaction audit events use the same correlation ID without payloads.

## Compatibility, migration and security limits

WP0 D1–D7 and accepted WP1–WP5 contracts remain controlling. No second Service administration system was added: WP3 owns Services, assignments, grant boundaries and approvals; WP6 consumes them. Platform I-AM approval/audit remains distinct from application-owned executable content. Blueprint export/import must not turn an application program or exported approval reference into live Service authority. Import requires separate review, current target-environment policy and exact new publication binding. This WP6 pass does not implement Blueprint orchestration.

The development-only protected host accepts optional server-side `triggerPublications` and `delegatedJobQueue` paths. Without a publication path, Service execution fails closed. The queue is host-internal and its root entry additionally requires a deployment-fixed Service and Trigger. Existing ordinary Trigger handlers and old registry rows remain current-actor compatible. Deployment must migrate Service-mode authoring from TypeScript to `program.json`, call the trusted owner publication bridge, and obtain a matching WP3 approval. Reusing an old artifact checksum or changing only a runtime row cannot authorize it. The WP1 development SQLite store adds a payload-free delegation audit table and additive audit columns; opening an older store creates/migrates them. No production data migration occurred.

Known limits: trusted application tooling must explicitly call the publication bridge; the general Artifact service's retired `publish` command and WP8 administration UI were not recreated. The job runner is a single-host execution/resume boundary, not a scheduler, distributed queue or general Workflow designer. A crash after marking a job running leaves it blocked for operator reconciliation; it cannot be blindly replayed. No production distributed revocation, IdP, MFA, or session lifecycle is present. A program approved to write Service-derived information into a User-readable Field can intentionally declassify it; the exact program, permission ceiling and target Field grants must be reviewed. Direct interpreter outputs and errors do not return protected values. A post-commit audit write failure cannot undo an already confirmed ORM commit; the durable pre-execution and program events remain, and DOE reports the truthful post-commit failure. Production Service delegation is not enabled by the development-only host guard. An OS-isolated general-TypeScript Service provider is a possible later design, not part of WP6.
