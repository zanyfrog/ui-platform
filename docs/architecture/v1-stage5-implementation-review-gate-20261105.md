## Implemented boundary

New `src/server/production/` modules are host composition factories, separate from the existing development server. They are exercised through local HTTP/HTTPS servers; they are not wired into the normal development server or a live target. No production launcher/activation is supplied by this Stage 5 increment.

- `oidc.ts`: trusted HTTPS discovery, exact configured issuer/client audience, RS256 configuration, established `openid-client` Code flow, S256 PKCE, random state/nonce, five-minute one-use browser-bound login transactions, exact callback and local return paths. It explicitly enables signed ID-token verification and requires recent MFA claims. No email/role claims confer authority. Unknown enrollment fails closed.
- `enrollment.ts`: Data-owned SQLite permanent issuer/subject-to-I-AM User links, separate application enrollment and revision, operator-capability approval/revocation and transactional audit. A subject can never be reassigned to another User. Active-User lookup is an owning-service port; it must be backed by I-AM on the target. Enrollment does not assign roles.
- `sessions.ts`: opaque random cookie sessions, server-side token digests, Secure/HttpOnly/SameSite=Lax `__Host-` cookies, CSRF/exact-origin checks, rotation, idle/absolute expiry, logout, local revocation and current enrollment checks. Restart invalidates sessions. No provider tokens are returned to browser code. `activeInternal` is a server-only status port, never a public session lookup.
- `internal-trust.ts` and `mtls-transport.ts`: mTLS plus EdDSA assertions bound to enrolled application/User/session, receiver-instance audience, release, method, path, body hash and range header. Maximum lifetime is 15 seconds; replay IDs are one-use. Known certificate fingerprints and signing key IDs must agree. Fresh receiver audience on restart prevents pre-restart assertion replay. Runtime forwards no browser bearer/cookies/actor headers. Current session/enrollment callbacks remain mandatory service ports.
- `current-iam.ts`: opaque leases and request attestation into the existing I-AM evaluator/planner and WP3 administration identity interfaces. Permission definitions, scope evaluation, role assignments and Dataset rules remain in I-AM. No Auth0 role registry or alternate permission evaluator.
- `releases.ts`: admission descriptor over an existing frozen `presentation/versions/vN/composition` tree, hashed bytes, selected release/app/schema checks, frozen metadata resolution and engine construction with mandatory release-aware planner guards. Forms/calculations, literal Stage 2 queries and record-delete actions resolve from server-selected definitions. Caller input contains locators and values only. Pointer changes during a before-insert Trigger prevent commit. There is no live-authoring fallback.
- `private-assets.ts`: private metadata/thumbnail/download/HEAD/range transport over version/hash records supplied by the owning asset manager; current I-AM admission is checked before lookup and again before response. It refuses links, outside-root files, foreign records and hash mismatches. Private storage is external to public release/export roots. Responses, including denials, use private/no-store; no conditional 304 bypass. Bytes default to attachment/octet-stream rather than trusting an uploaded media type.
- `runtime.ts`: explicit public-file allowlist plus authentication and bounded protected endpoints. No Builder router, management import, source export, developer proxy or filesystem store. Auth/protected routes require TLS or an explicitly configured trusted proxy peer with HTTPS forwarding metadata. Public runtime receives only public bytes and its own session/service ports.
- `data-handler.ts`: actual mTLS-to-current-I-AM-to-release-to-DOE HTTP composition. Raw Dataset APIs and management routes have no runtime forwarding path. `management.ts` is a **Data-owned internal management listener**, intended only for the separately credentialed management frontend; it reuses WP3 stage/activate/provision and current I-AM. It does not grant the Builder process direct policy-file credentials.
- `src/shared/released-runtime-services.ts`: browser transport preserving existing Form/service signatures while sending only release/artifact/action locators and values with a server-issued CSRF token. It never sends actor/role/definitions and never automatically retries a write.

The supported protected action subset is deliberately explicit: existing Form create/edit/read-back, literal Dataset read queries with declared scalar filters, record delete and persisted calculations. Arbitrary function/service/Workflow execution, unsupported Form mode overrides and unsupported contract versions fail closed. They are not silently interpreted as protected release contracts. Full saved-website publishing/admission and private thumbnail presentation still need integration evidence on the real selected application; the service tests do not claim that journey is complete.

Production deployment packaging must carry the nested security module's manifest/lock and use its pinned dependencies. Root dependency resolution was not refreshed. Exact new library versions: `openid-client` **6.8.9**, `jose` **6.2.15**, transitive `oauth4webapi` **3.8.8**, with registry integrity pins in `src/server/production/package-lock.json`. Installation used `--ignore-scripts` into that module only. The new modules and browser adapter pass focused strict TypeScript checking on **Node 24.19.0, Windows**. This is not Linux compatibility evidence or a claim that the entire historical application now passes its broader typecheck.
