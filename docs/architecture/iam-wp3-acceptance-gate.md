`@ui-platform/i-am/administration` uses WP1 documents and the WP2 evaluator. A host supplies authenticated actor handles, attested evaluator requests, a trusted scope authority, and a separate strong D6 recovery verifier. Staging through text, CLI, API or UI creates only a draft. Activation checks the current actor's security-admin permission and Grant Boundary; inside WP1's serialized SQLite transaction it validates the full resulting graph, ownership, effective grant closure, self-escalation, last-admin continuity and mandatory audit. The store records a durable one-way WP3 mode, so the older WP1 `--actor` activation cannot commit to an opted-in authority. The new CLI adapter requires a host-authenticated context and uses the same service gate.

The SQLite schema additions are additive. Constructing the WP3 service sets a durable one-way protection bit on that authority. From then on, callers using the WP1 activation API/legacy CLI must migrate to a trusted WP3 host adapter; their draft validation/staging remains available. DOE now intentionally rejects ordinary access to the legacy raw I-AM grant and membership datasets even if an old grant names them. Internal I-AM repository access and the legacy root package contracts remain intact. No existing grants or credentials were automatically migrated, and no administrator was seeded.

## Limits and next gates

This is a development acceptance implementation, not a production cutover. `SecurityAdministrationService` rejects `NODE_ENV=production`; the deployment must provide production authentication, designated recovery operators, strong proof and protected control-plane storage before that guard can be reconsidered. The SQLite store and its in-process API are trusted infrastructure, not a sandbox against arbitrary code or direct database writes in the same process. Denied attempts return bounded diagnostics; the required durable audit covers successful privileged mutations and recovery, with rollback on audit failure. Multi-host operation and cross-process session revocation are not claimed.

WP4 Dataset/Field authority and plans, WP5 DOE enforcement, WP6 delegated Service execution, WP7 production identity/session infrastructure, WP8 final administration UX/Blueprint orchestration, and WP9 hardening/cutover remain deferred. No commit, push, deployment, migration, release, or WP4 work was performed. **Stop at the WP3 acceptance gate.**
