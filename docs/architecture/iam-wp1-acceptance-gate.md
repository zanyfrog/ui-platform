## Implemented WP1 slice

The Data Services I-AM package now has an additive `@ui-platform/i-am/definitions` subpath for typed User, Service, Person link, Permission, Permission Set, Role, Group, Service requirement, and assignment records. The existing package-root evaluator and DOE contracts were left untouched. A shared parser rejects unknown fields, duplicate JSON keys, invalid IDs/dates, unsupported versions and executable predicates. Graph validation rejects missing/cyclic set references, unauthorized cross-application references, unpinned shared set references, duplicate Person links, overlapping duplicate assignments and Service assignments outside a Service's application. Definitions can be staged without changing the active revision. An explicit activation revalidates against the current graph and atomically commits definitions, revision and audit in an isolated SQLite authority. A development CLI, stage-only file watcher and offline legacy-grant dry run call the shared service. The WP1 API is deliberately development-only; it has no production authentication, grant ceiling, last-admin enforcement or protected administration endpoint.

The existing UI Platform portable ZIP exporter now refuses an application with a `security/` root. That prevents its broad directory copy from exporting security state before Blueprint has a validated allowlist. It does not implement Blueprint export/import. Platform identities, credentials, sessions, real Services, approvals, grant boundaries, active state and audit remain outside portable application definitions. Application-scoped User assignments are operational state and remain outside normal Blueprint export. Portable Service requirements are desired definitions, never actual Service grants. Blueprint remains the future orchestrator; I-AM supplies the provider/contract through a normal package dependency. This dependency/provider is not wired into an application yet.

## Contract reconciliation before WP1 can be accepted

The implemented v1 `scope` shape is `{ applicationId, resource?: { kind, id, parentId? } }`, while the approved WP0 file examples use `{ resource: { authorityId, applicationId, kind, id }, descendants }`. The source parser cannot currently read those examples. The WP0 file-format proposal also includes protected `security.application`, `security.grant-boundary` and `security.service-use-approval` artifact types; these do not yet have WP1 schemas/registrations. Some of their administration semantics are later waypoints, but the file-format boundary must be explicitly reconciled before calling the WP1 definition model stable. A pinned shared set reference currently proves presence of revision/digest fields, not that the dependency matches an approved immutable publication. Dataset/Field IDs are accepted as strings; authoritative resource registry binding and rename proof remain WP4-dependent and must not be claimed as WP1 evidence.

## Gate decision

WP1 cannot pass its own acceptance gate while W1-06, W1-07 and W1-08 are open and the scope/file-format mismatch is unresolved. Keep this definition plane isolated from protected data and production administration. Continue WP1 only under a subsequent instruction; **do not start WP2 from this record**. The next WP1 work is to reconcile the source shape with WP0, register strict artifact schemas, connect actual UI/API authoring to the shared service, exercise file reconciliation and complete the acceptance fixtures. D6 recovery is a separate platform-level trusted I-AM capability with deployment-designated operators, strong authentication and mandatory durable audit; it is not an application Role/Group or auto-seeded administrator.
