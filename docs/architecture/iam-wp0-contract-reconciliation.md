## Canonical terminology and ownership

| Term | Contract meaning / owner |
| --- | --- |
| Person | Domain record; never an authorization subject. Optional link keyed by Application ID + Dataset ID + typed record key. |
| User | Permanent platform principal; authentication identities link to it through unique provider+issuer+subject bindings. One User may link to multiple Person records; a Person record links to at most one User. |
| Service / System | Distinct principals. Service receives Permission Sets through Service Assignments. System is explicitly trusted infrastructure, never an implicit superuser. |
| Actor / security context | Authenticated principal plus security-session/credential evidence, created by trusted host code. A serialized ID or TypeScript type is not proof of identity. |
| Role | Reusable responsibility definition referencing Permission Sets, assigned to a User at a scope and time interval. No Role inheritance. |
| Group | Application-owned User collection referencing Permission Sets. No nesting and no Role links. |
| Permission / rule | Permission is a stable atomic capability definition. Rule applies ALLOW/DENY for that capability to a scope, optional rows and fields. Friendly names are aliases, not identity. |
| Permission Set | Named, versioned bundle of rules and included sets. Directed acyclic graph; flatten semantics, preserve every provenance path. |
| Definition / assignment | Definition describes reusable structure. Assignment/membership is a dated, audited fact; neither creates a User. |
| Resource | Owner-registered permanent ID plus kind, parent and Application identity. Retired resources retain historical resolution. |
| Platform-owned / Application-owned | Ownership is an authority boundary recorded by the trusted registry, not inferred from a folder or copied manifest. A System actor is a principal type; it is not the definition-owner label. Storage may share one database while ownership remains distinct. |
| Grant boundary | Separately delegated administrative ceiling; possessing a business permission does not convey permission to grant it, or vice versa. |
| Draft / active revision | Editable candidate bytes versus the validated, authorized policy snapshot used for decisions. A valid draft need not be activated. |

## Proposed evaluation semantics

These details were approved at the WP0 contract gate; they do not describe existing runtime behavior.

1. Assignment intervals use UTC RFC 3339 instants, start inclusive and end exclusive (`start <= now < end`). Null start on memberships means unbounded past; Role/Service assignments require a start. Null end means indefinite. Reject end <= start. Prohibit overlapping same User+Role+canonical scope assignments even if one is inactive; edit/archive the existing assignment instead. Apply the same duplicate protection to memberships and Service Assignments. Adjacent intervals are valid. Definition/principal/assignment must all be active; archive is terminal for use, with history retained.
2. Permission ownership and applicability are explicit. Example atomic capability `dataset.records.view` has a permanent ID and supports Dataset/Field/Record targets; UI displays `employees.view`. Application scope descends only for capabilities declaring that target kind; it never flows upward or sideways. Application A cannot consume B's sets; approved shared/system packages are pinned by revision and integrity digest.
3. At each resource/row/field: `effective = any applicable ALLOW AND NOT any applicable DENY`. Union ALLOW row predicates, union DENY predicates, subtract denies. Do not choose the first scope. Each field retains its own predicate; a salary ALLOW for row A cannot combine with an unrelated row B ALLOW to expose salary on B. Dataset-level eligibility and field eligibility are both required. A field rule does not grant visibility of an otherwise denied record.
4. Reads omit unauthorized properties, preserving legitimate nulls. An explicitly denied operation fails even for `select: []`. Queries validate filter, order, group, aggregate, join, computed-field dependencies and export fields before reading. Proposed conservative v1: inference use requires unconditional field read access over the candidate row domain; otherwise reject (even if per-row projection could have been safe). No hidden-field inference through totals or pagination. Unsupported query constructs fail closed.
5. Inserts evaluate final new rows; deletes evaluate old rows; updates evaluate old and proposed final rows (including ownership changes). All requested and transformed fields must be authorized. Defaults are writes too; no implicit exemption for trigger/default/server changes. A separate approved Service operation is needed for privileged work. Any pre-commit security failure poisons and rolls back the root transaction, including bulk/nested requests. Reject partial-security writes even if legacy `atomic:false` or `unauthorizedWriteBehavior:"filter"` was supplied. Preserve truthful committed/unknown outcomes for afterCommit failures.
6. Expressions contain only registered operators, permanent field IDs, typed constants and allowlisted trusted actor/context facts. No JavaScript, dynamic property traversal, network calls or user-supplied facts. Missing/type-mismatched facts, malformed trees and unknown fields make the decision fail closed; they never become an unrestricted predicate. Relationship facts are server-owned and revision-bound. Limit nesting/node counts; do not truncate provenance into an incomplete authorization computation.
7. `can`/`canAny` are convenience decision probes; they never confer a reusable execution capability. A conditional ALLOW means DOE must enforce the returned row/field plan; it is not permission for an arbitrary record. Explain-access for another User requires a separate diagnostic capability and redacts sensitive rule/fact data.

## Proposed resource and execution contract

Resource identity is the tuple authority + Application ID + kind + permanent ID. Field IDs are qualified by their Dataset parent. Record identity includes Dataset ID and a typed primary-key value. Namespace/environment remains a deployment binding, not a second unreviewed tenant boundary. If namespace denotes tenancy in any deployment, migration must block until it maps to a distinct approved security Application/tenant domain. Never silently discard it.

Registry adapters resolve mutable names to IDs and applied schema revisions, then map IDs back to physical keys for DOE. Dataset schema identity and `DefinitionRef.definitionId` (currently often name-derived) are not interchangeable. Preserve stable owner IDs on rename. Recreated same-name resources receive different IDs; retired IDs cannot be reused. Published-but-unapplied schema does not establish runtime field identity. Application cloning requires explicit new IDs and policy rebinding.

## Platform/Application ownership and Blueprint portability

This fills a WP0 omission identified after the initial D1–D7 approval. It records the agreed ownership and Blueprint rules from the prior architecture discussion. Blueprint owns export/import orchestration and formats; I-AM supplies the security-definition contracts, validation and authorized activation. This section does not create a separate I-AM export system.

| Security object | Authoritative owner | Blueprint treatment |
| --- | --- | --- |
| User, actual Service identity/credential, authentication binding, Person link, session/MFA state, System principal/profile, recovery capability/operator | Platform/deployment identity authority | Normally excluded from portable Application/Blueprint export. A Service may be approved for an Application without its identity becoming Application source. |
| Atomic platform capability and protected platform Role/Permission Set/grant boundary | Platform security authority | Reference by stable ID and compatible revision/digest; do not copy, edit or redefine in the target Application. Missing or incompatible dependency blocks import. |
| Approved reusable shared-package Permission Set/capability | Shared package authority | Carry a pinned dependency reference; target must resolve/approve the same package identity and compatible revision/digest. No silent cross-Application copy. |
| Application security configuration, application-owned capability/rule, Dataset/Field security, Role, Group, Permission Set | Source Application authority, using owner registries for Dataset/Field identity | Portable **definition templates**. Rebind to a new target Application ID and newly issued definition/resource IDs; stage as drafts and activate under target authority. Group members and Role holders do not travel. |
| Application-owned Service requirement/configuration | Source Application security authority | Export a non-secret provisioning requirement/template. Target Security Administrator must create or approve a new platform-managed Service principal and its Permission Set assignment; no credential or ready-to-run principal travels. |
| User→Role assignment, User→Group membership, Service assignment/use approval, administrative ceiling | Platform-managed operational security records scoped to an Application | Normally excluded from portable export. Same-installation backup/restore or explicit migration with identity mapping may handle assignments under separate validation/audit; a portable Blueprint never turns them into effective target access. |
| Trigger/Workflow execution selection | Executable owner plus security approval authority | Export executable definition with an unresolved Service execution requirement. Target approval must bind the target executable ID/digest, Service, capability and permission ceiling before activation. |

Blueprint's security provider reads verified definitions from each owning security/resource registry and uses an explicit allowlist of portable types/fields. It walks all security and resource references; unresolved, cross-Application or unauthorized references block export, rather than dropping them. Blueprint's manifest records source IDs, a deterministic content digest, owner classification, platform/shared dependencies, and unresolved deployment bindings. It excludes active policy pointers, historical assignment/audit data, secret material, runtime caches and personal/application records. An export archive is an editable representation, not a security authority or grant.

Blueprint import verifies package integrity and supported format, maps every source Application, Dataset, Field, artifact and application-owned security-definition ID to new target IDs, rewrites internal references and row predicates, and records that map for review. Platform/shared references are resolved against the target authority and remain references. A conflicting name never authorizes reuse of an existing target ID. Missing, retired, incompatible or ambiguous references block staging/activation; no best-effort omission of a DENY or Service approval. Blueprint sends proposed definitions through the same I-AM/owner service used by UI, CLI, API and text reconcile; it does not write authoritative security storage directly. Import stages drafts, then a separate authenticated target-Application operation performs grant-ceiling, protected-definition, last-admin, Service-use and audit checks before activation. The imported Blueprint creates no User, membership, assignment, credential or effective permission merely by being loaded. A target deployment establishes its own valid administrator anchor under the approved D6 rule.

`@ui-platform/i-am` is a normal application package dependency resolved by the existing package/export mechanism for a standalone application. Blueprint carries the application's security design and dependency metadata; it does not copy the I-AM package as application-owned source or serialize a running I-AM authority. The target deployment provides the platform identity/session authority and configures its single policy authority. The I-AM management UI belongs in reusable UI/management packages and consumes the same headless I-AM services; WP8 owns the UX, while server/DOE enforcement remains authoritative.

Existing UI Platform `exportApp` is a portable application export, not a Blueprint security export. It currently copies the Application directory broadly and vendors packages; it has no I-AM allowlist, identity remap or target activation path ([source](../../src/server/exporter.ts)). It must not be presented as implementing these Blueprint rules. Before future security files are stored in an Application tree, the export path needs a security-aware allowlist and secret/assignment exclusion or it must refuse an export that could carry them. The older artifact-foundation waypoint names Blueprint Import/Export as a future consumer of normalized artifacts, not as an existing security boundary ([source](artifact-foundation-v1.1-waypoint.md)).

OperationContext retains operation/root/parent/correlation IDs, lifecycle, transaction and commit outcome. Add original initiator, current executor, authenticated context and immutable delegation steps. Keep the old `actor` only as a deprecated read projection of the current executor during transition. Trusted runtime owns the real context; handler-visible DTOs are detached/frozen. No request field can modify it. This is containment within trusted host code, not a sandbox for arbitrary Node plugins.

Resolve the architecture's nested-trigger ambiguity as follows: `inherit` (UI label **Initiating User** for an ordinary root User operation) retains the current executor of the incoming operation. Thus Mary → A[Mary] → B[Service] → C[inherited Service] works as section 27 specifies. It does not reset C to Mary or impersonate her. Service/System initiated jobs retain their principal. Explicit Service selection requires approved application+Trigger/Workflow+capability+executable digest/revision; editing executable scope invalidates approval unless a reviewed constrained execution profile proves equivalence. Recheck at activation and execution, including resumed jobs. Existing Service business permissions alone are insufficient.

A Service-executed hook cannot smuggle privileged fields into the caller's pending write: the parent's final payload is still checked under the parent executor. Privileged changes use an explicit Service-authorized nested DOE operation with its own decision and preserved chain. Broad all-field grants intentionally cover future fields of the supported resource kind; explicit field lists do not. Schema activation must surface this access impact for review, and migrated legacy field coverage must be reported rather than silently expanded.

## Proposed policy authority, administration and revocation

Use one authoritative I-AM control plane per deployment/environment, with a monotonic policy revision and separately checked principal/session/resource/fact revisions. All consumers use that authority through the same decision interface; embedded mode is allowed only when it is the sole authority. Recommended first distributed deployment uses an authenticated remote adapter. Separate administration credentials/capabilities from evaluation transport, and never use a shared development bearer as principal proof. Do not combine two default policy stores or rely on shared-directory caches.

Activation linearizes a validated policy revision, audit intent/outbox and active pointer as one durable transaction. Administrative writes use compare-and-swap against the expected policy revision and atomically re-evaluate grant ceilings, self-escalation and last-admin invariants against the proposed graph. The current file ORM does not supply a proven distributed transaction/durability boundary for this; WP1 must choose a qualified store or remain explicitly isolated/non-production. A file watcher is not that authority.

Grant boundaries list assignable Permission/Scope/Service-use envelopes and permitted security operations. Evaluate the complete transitive delta of Role, Group, set, membership, assignment and Service changes, including reactivation and edits to dates. The ability to edit a container never bypasses the ceiling. Arbitrary predicate implication is not inferred: v1 accepts only identical or registered narrower scope templates for grant ceilings, otherwise rejects for higher-level review. Removal of DENY can increase access and is checked as a grant. Protected grant-boundary definitions cannot be expanded by their beneficiaries through ordinary security editing.

Last-admin protection runs under the same serialized mutation as activation and examines all principal/definition/assignment paths. Each managed Application has at least one active, non-expiring Security Administrator path; future-only or expiring coverage cannot count as the sole anchor. Bootstrap/recovery authority is a separate platform-level trusted I-AM recovery capability, never an Application Role/Group or automatically seeded administrator account. Each deployment designates its authorized recovery operator(s); use requires strong authentication and mandatory durable audit. Recovery does not silently waive the last-admin invariant: it establishes or repairs valid administrator coverage through a controlled, audited operation.

After a successful security change, every newly admitted decision checks authoritative current revisions and principal/session validity; cache entries and TTL alone cannot authorize. During authority failure or partition, deny. Timed assignment boundaries bound decision expiry and are re-evaluated using trusted time. Existing admitted work may finish under its snapshot; child operations, resumed jobs and final transformed-write authorization are new decisions. No claim of retroactively undoing confirmed commits. A stricter cancellation policy would be a separate decision.

Audit captures actor/initiator/executor, chain, operation/decision/change IDs, time, scope, old/new security values, policy revisions and reason where required. Store secrets as credential references only; protect/redact sensitive policy diffs and facts. Durable security-change and delegation audit is a precondition to activation/elevation. Operation audit uses a durable outbox where supported; a post-commit sink failure creates pending delivery/operational failure, never a false rollback. Routine reads may use diagnostic logging. Retention, access and tamper-evidence must be accepted at WP9.
