# WP0 compatibility and migration proposal

**No migrations run. No runtime, packages, locks, policies, credentials or published definitions changed by WP0.** D1–D7 are approved as contracts; a separate instruction is required for WP1 implementation. [Approved decisions](../iam-wp0-contract-reconciliation.md) and the [acceptance matrix](acceptance-matrix.md) govern implementation.

## Contract transition

V2 DTOs are not assignable to old partial decisions. |

## Sequenced migration runbook (future authorized work)

1. Inventory each deployment's roots, independent I-AM stores, Users/Services, grant subjects, namespace usage, Dataset/Field identities, editor fixtures, direct-ORM callers and protected ingress. Do not inspect/export credentials or personal rows merely to inventory policy. Identify which store is authoritative; conflicting standalone/embedded roots require owner resolution.
2. Back up complete policy bytes, schema/application identity mappings and immutable history. Record hashes, actor and maintenance scope. Capture a policy revision/writer fence; refuse import from a changing source. Trusted migration runs below DOE only for the named internal repositories, with maintenance access and audit.
3. Generate an offline dry-run changeset and manifest: source hashes, legacy→new ID map, all defaults, unknowns, deactivated/orphaned grants and rule differences. Classify results as equivalent, intentional restriction, or unresolved. Do not import unknown Subjects as active Users. Do not migrate Scouts role catalogs or data.
4. Review synthetic differential authorization cases, including multi-scope fields, no-select queries, malformed policies, app boundaries and old/new writes. A legacy unsafe allow is not an equivalence target. Every restriction or newly supported behavior is documented; every ambiguous policy blocks that portion of activation.
5. Import drafts through the shared pipeline. Validate referential DAG, statuses, dates, grant boundaries, last-admin continuity and credentials. Bootstrap the first security administrator using the separate platform-level trusted I-AM recovery capability, with strong authentication, a deployment-designated authorized operator, mandatory durable audit and an explicit recovery procedure. Do not create an Application Role/Group for recovery or automatically seed an administrator account.
6. Shadow-evaluate v2 decisions without using them as production authorization until the applicable WP2–7 evidence passes. Log redacted mismatches and resolve them; never OR legacy and v2 allows. Definitions may be implemented in isolation at WP1, but real protected data cannot rely on incomplete later gates.
7. At approved cutover: fence writers, recheck snapshot hashes/revisions, commit new active policy/audit, bind every consumer to the same authority, invalidate legacy caches/sessions as required, and deny legacy production ingress. Test from fresh independent processes. If some clients remain legacy, keep the affected protected application unavailable rather than fall back to legacy policy.
8. Monitor denied operations, revision lag, audit delivery and compatibility. Retain old data as read-only evidence. A rollback requires a reviewed reverse compatibility plan; restored legacy security is not an automatic safe fallback. If safety cannot be proved, keep ingress closed, restore data consistently under maintenance, and publish an authorized corrective revision.

Blueprint movement is a separate path from legacy grant migration. A Blueprint's source ID map, dependency pins and target binding plan must be reviewable before import activation. Import must not treat a copied Role/Group/Permission Set definition as a User assignment or treat a copied Trigger Service selection as target approval. The existing portable application exporter and future Blueprint exporter need distinct format labels; consumers must reject a generic application ZIP as if it carried Blueprint security metadata. Application package export may include application-owned security source definitions only after its allowlist and redaction boundary are implemented and tested.

Blueprint owns both export/import orchestration and its manifest/formats. I-AM supplies the security-definition contracts, read/validate/stage/activate services and the security-section provider; it does not create a second I-AM exporter. `@ui-platform/i-am` is resolved through the normal application package dependency mechanism, rather than copied into the application as source. Same-installation backup/restore and explicit identity-mapped migration are separate authorized workflows that may preserve application-scoped User assignments; portable Blueprint import normally excludes them.

## Non-goals and existing limitations carried forward

No rewrite of ORM into an authorization engine, no change to confirmed/unknown commit outcomes, no physical schema migration as a side effect of policy conversion, no fixture role promotion, no provider choice or credentials creation, and no weakening of accepted scoped-write containment during transition.

IAM-0's unresolved items remain open: DS0-HTTP-QUERY-ERROR; DS0-APPLIED-VALIDATOR; intermittent editor cleanup/timeouts; Windows watcher EPERM; non-atomic multi-file ORM durability and absent writer fencing; stale owner/state-lock recovery; legacy/external deployment certification; applied-state authority integration; publication/runtime Trigger integration; scoped-write support; schema upgrades; hosting/security/audit readiness; historical STAB-2 byte qualification; missing original DS0 plan/formal WP1 conditions. WP0 does not reclassify any of these as resolved.

## Package and operational rollout boundary

Implementation spans at least Data Services I-AM/DOE/Schema/Trigger contracts and UI Platform artifacts/editor/CLI composition. UI Platform currently has no root dependency on I-AM/DOE, so wiring is a real package/version/host change. Do not add dependencies or edit sibling repository code at WP0. Future releases must publish coherent adapters and supported version pairs; mixed versions fail contract negotiation closed.

Application owners approve identity/resource mapping; security administrators approve imported grants within ceilings; the deployment designates authorized recovery operator(s) and platform operators approve policy authority, maintenance/bootstrap and deployment cutover. These are future rollout responsibilities under the approved D6 boundary, not requests to authorize them now.
