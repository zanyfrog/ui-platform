# V1 Page Builder — Shared Website Composition Review Gate

2026-10-28. **Read-only assessment; no implementation or browser qualification performed.** Multi-Page Website Authoring is accepted and closed in its separate closure document.

## Recommendation

The next most valuable increment is one shared website Shell containing a branded header, one Home/About/Contact menu and a footer, with a single `region-main` for each Page's unique content. Demonstrate editing the shared header/footer once and seeing the result on all three routes in the disposable website and saved Design Preview. Use existing HTML, composition metadata, menu files and the shared renderer. Defer a general theme designer, multiple templates, nested menus and responsive navigation drawers.

Prefer a fresh bounded composition fixture and fresh Pages for initial qualification, preserving all accepted plain Pages. If adoption of existing plain Pages is required, make that an explicit, separately specified conversion within the same proposed increment; never silently assign a Shell and imply the body will render correctly.

## Gaps that determine the implementation boundary

1. **Composition entrypoint:** `mountCompositionManager` returns when no composition definition exists. `compositionWorkspace` requires composed Pages to have permanent Route and Shell identities. Current plain Pages lack route IDs. Existing legacy Presentation initialization is not proof of ordinary composition-v1 setup. Trace and expose one bounded setup path using existing owner services and composition settings, with no implicit conversion or changes during this assessment.
2. **Plain Page adoption:** `changePageShell` calls `remapPageRegions`, changes shellId and filters metadata to retained IDs. It does not establish a plain-body-to-main-Region conversion or assign a missing routeId. A plain Page body is not extracted by `mountComposedPage` because it has no Regions. Therefore current Change Page Shell is not sufficient evidence that adopting the accepted three Pages preserves visible content. An explicit conversion would need a managed main wrapper, byte/identity-preserving content containment, one-time Route identity admission, complete validation and clear failure behavior. It must retain all existing artifact IDs and existing route IDs; accepted originals should remain untouched during qualification.
3. **Host admission:** `revision-vite.ts` explicitly refuses a composed Page without the revision-aware `applicationComposition` plugin. The accepted disposable host only installs `visualArtifacts`. Read and qualify the existing composition plugin's graph/dependency/recovery-refusal contracts before adding it to a fresh bounded host configuration. Do not weaken refusal or treat the plain-host qualification as composition qualification. This is a genuine prerequisite, not a reason to build another renderer.
4. **Runtime and Preview navigation:** current multi-Page literal-click handling is enabled for plain Pages and is disabled for Shell-backed Pages. Saved Preview likewise only resolves cross-Page destinations for plain Pages; its composed navigation adapter currently retains the earlier logging behavior. Existing menu-generated actions can reuse the host adapter, but composed Preview destination loading must be connected to the existing authorized saved-graph read, iframe URL/history and disposal lifecycle. Preserve same-Page anchor acceptance; do not promise anchors inside composed Regions in this increment without separate scope.
5. **Reference safety:** existing composition validation checks identity destinations and the existing Shell deletion guard protects default/used Shells. Verify Page deletion/route changes against menu destinations and surviving literal links in the proposed scope. The newly accepted plain-Page scan is not a general composed-menu protection guarantee. Add only a proven missing guard under existing mutation authority; no general graph framework or cascade rewriting.
6. **Polish through ordinary controls:** current manager edits existing theme entries and selects existing stylesheets; this does not establish a complete visual stylesheet authoring workflow. Shell selection/mapping uses identity prompts in places, and Region placement can be awkward. Limit initial ordinary controls to a clear Shell choice, main-content Region, branding fields, menu editing and a small validated style set. Verify keyboard focus, active menu indication and a basic narrow viewport. A sophisticated responsive menu or theme editor is separate work.

## Proposed bounded implementation and evidence

Provide one ordinary composition setup flow and one Shell with header, menu, main Region and footer. Create three fresh Shell-backed Pages at explicit routes, with stable identities, and edit their unique HTML through existing Page controls. Author one menu through existing destination controls; edit the Shell brand/footer once and verify all Pages update after Save/Reload. Reuse the existing runtime, menu projection, asset service and composition graph.

Qualify the existing composition plugin in a disposable host, preserving recovery-free admission and narrowly pinning Shell/Page/style/asset/package inputs. Extend the existing saved Design Preview lifecycle only enough to navigate these saved composed Pages, retain exact saved revisions, dispose old mounts and keep URL/history inside the iframe. Verify mouse/Enter, direct website loads, Reload, Back/Forward, focus/scroll, active menu state, main Region inheritance/empty overrides and refusal of unsafe references. Preserve accepted plain-Page anchors and multi-Page workflows with focused regression checks.

Do not alter accepted Pages to manufacture the demonstration. If existing-Page conversion is selected, review its concrete source/identity transformation and transaction boundary before implementing it. Existing serialization remains a cooperating-writer boundary, not a multi-artifact atomic migration guarantee.

No new rendering system or routing framework is justified. The unresolved host composition qualification and missing demonstrated ordinary setup/adoption path are real prerequisites; this assessment does not assert that they are unsafe or impossible. If the existing plugin cannot maintain recovery refusal within bounded inputs, stop with the exact conflict rather than expanding permissions or admission.

No implementation, product/configuration changes, commits or pushes were performed for this assessment. No production, comprehensive security, cross-Page fragments or deferred unsaved-draft Preview acceptance is implied.

Stop: **V1 Page Builder — Shared Website Composition Review Gate**. Separate authorization is required before implementation.
