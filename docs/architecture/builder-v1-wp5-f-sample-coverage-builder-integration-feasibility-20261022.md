## Ordinary Builder editing checks without a real backend

The currently accepted harness exercises `EditingLifecycle` beside the panel, not ordinary source editing. There is a safe route to stronger but still limited evidence:

1. Use real `EditorRuntimeContext`, `EditorWorkingCopy` and the actual `renderSourceEditor` with a synthetic generic Artifact DTO. Context already accepts an `ArtifactEditorTransport` factory. Use in-memory load/save/validation/reference callbacks; compare raw source, baseline/checksum, dirty/pending state, generations, identity and real Undo/Redo. The source editor is a native textarea renderer; no Monaco dependency was found in this inspected path, so no Monaco claim should be made.
2. Context `open()` still calls `refreshEditorSession`. Install a test-only, exact synthetic session response before module initialization, using a narrowly scoped in-memory fetch facade; all other URLs fail. This is simulated session plumbing, not authorization qualification. Do not call the normal session endpoint or use ordinary cookies/tokens. Context imports transport/session/client-copy recovery modules, so their whole selected closure must be inspected before any future execution; WP2 recovery actions are not exercised, and no Foundation recovery path is involved.
3. Couple the real source editor/context to `BuilderWorkspaceCoordinator` through its existing injected authorize/mount/subject callbacks. Return fixed synthetic owner-qualified identities. A test adapter delegates edits/history to the real context and source renderer. A fake authorization result is not real Builder access admission, and a test adapter is not `mountWorkspaceEditor` integration. Verify tab deactivation/reselection, source-file/caret selection and retained dirty drafts in this explicit boundary.
4. Extract only the existing fixture-panel presentation binding from Builder shell into a small shared helper if needed to test the exact production binding. It may receive read-only identity/dirty status and invalidation notifications; the Preview panel/frame must still receive no editor, save/flush or transport object. No alternative editing lifecycle or production authorization seam is proposed.

The normal `builder-workspace/shell.ts` cannot simply be imported into the dedicated harness: it imports broad editor adapters and creation flows, performs discovery/authorization, and starts a two-second authority poll. `mountWorkspaceEditor` includes live request/session bindings and default generic editor transports. `mountEditorShell` imports default plugins; those include Dataset tools and the old Form preview. The old `form-preview.ts:show()` flushes dirty source before opening, and the ordinary Visual preview has live package/service/capture paths. These are excluded from the next harness. Do not click or reuse old Preview controls as evidence for the restricted fixture panel.

Actual source-editor/context/coordinator checks are a meaningful increase over lifecycle-only tests, but they still do not close full normal Builder shell/adapter/backend integration, actual saved-artifact rendering, protected concurrency or trusted revocation qualification.
