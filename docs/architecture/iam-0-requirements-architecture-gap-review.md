Date: 2026-09-30. **Read-only architecture/source audit; awaiting IAM-0 review.**

## 1. Finding and scope

UI Platform has useful, separately bounded security foundations, but **not an integrated production I-AM system**. Data Services implements a small allow-grant evaluator and DOE enforcement. UI Platform implements development-only artifact-editor identities, sessions and authorization. Neither is a complete authentication, administration, revocation or audit solution for applications and platform management.

The existing separation remains sound: **I-AM decides; DOE enforces application-data access; ORM persists**. Do not move general authorization into ORM or reproduce permission resolution in Forms, Pages or editor components. Trusted I-AM internal persistence is an intentional exception to the application-data path, needed to avoid circular authorization.

The highest-priority gaps before any milestone exposes real protected data or privileged actions are authenticated actor binding, consistent policy authority, complete query/write enforcement contracts, administrative separation, and an explicit revocation/audit model. UI-only development can be selected without completing every I-AM feature, provided its boundaries and unavailable secured behavior are explicit. G5's isolated, synthetic runtime acceptance does not certify production security.

### Exact enforcement boundary and important qualifications

Current write path: supplied actor/request → exact operation allowlist → ORM definition lookup → I-AM decision → deny / scoped-write rejection → normalization/defaults → transaction → before trigger → ORM write → after trigger → commit → afterCommit. Nested children re-enter DOE with the parent actor and private execution session. Pre-commit child failure poisons the root even if ignored; confirmed parent commit survives a failing afterCommit child. No IAM-0 change to those accepted guarantees is proposed here.

The package contract says triggers do not get raw ORM or mutable security state. The supplied trigger facade has no ORM, but `Readonly<OperationActor>` and readonly record arrays are TypeScript constraints only: `run` passes object references, not a frozen actor/security capability. The existing normalization test deliberately edits objects within `newRecords`. A registered JavaScript handler can also capture an ORM from its host. Treat handlers as trusted code today. Decide runtime immutability, transformed-field authorization and privileged-handler rules before treating plugin isolation as enforced. This is a source-level boundary risk, not evidence that an accepted test failed.

### Scouts security caveats that must not be copied

**S-REF-1 — Development authentication bypass is not a secure boundary.** `server.js:67` treats either a loopback peer **or the client header `x-local-demo-login: true`** as local-demo eligibility. `/auth/login` with no password then passes `allowPasswordless` to the engine. The engine skips password verification; MFA remains conditional on administrator role and `mfaExempt`. Thus the network handler supplies the supposedly explicit bypass from client-controlled input, without a development-environment gate. The HTTP server's `listen(port)` supplies no loopback-only bind. This is code-path evidence; no attack was executed.

`local-demo-sync.js:86–126` creates accounts with a fixed demo password and sets `mfaExempt`/`localDemoAccount`, including on existing matched accounts. Sync is invoked on server startup and passwordless login. It can mark accounts/people active. Do not copy account synchronization, password defaults, exemption behavior or startup side effects. Do not run this reference service against real stores merely to review it.

**S-REF-2 — Service-token design is insufficient.** `server.js:10,62,241` has a hardcoded fallback service token and allows policy-snapshot access by loopback peer without a token. Catalog/demo sync sends that same token to another service. No per-service identity, audience, expiry, rotation, revocation or least-privilege capability mapping is established. Loopback/proxy placement is not identity. The value of the default token is intentionally not reproduced here.

**S-REF-3 — Session revocation and account status are incomplete.** `authenticate` checks session status/expiry but does not reject based on account/person active status before returning access. `updatePersonStatus` does not revoke sessions. Some derived roles disappear when inactive, but existing global assignments, unit roles and parent relationships remain independently evaluated; `authorize` gives a legacy administrator an early allow. Password/MFA reset does revoke sessions. No general guarantee that deactivation removes every permission is supported. The inactive-member test is narrower than that guarantee.

**S-REF-4 — Separate role labels do not guarantee separation of duties.** Security routes select capabilities such as `admin.roles.manage`, but `assignRoleToPerson` permits assignment of any existing role without a grant ceiling, self-assignment prohibition or second approver. A security administrator can therefore grant an ADMIN role through the reviewed route/call chain. Permission-set editing similarly lacks a demonstrated delegation ceiling. Final-administrator protection prevents selected lockouts; it does not prevent escalation, and not all legacy mutation paths use it. These are reasons to design generic administrative capabilities, not reuse the built-in role hierarchy.

**S-REF-5 — Audit, policy and storage are not production guarantees.** Security changes record old/new values and an actor parameter; several legacy methods instead label the target person as `actorUserId`, and general routes do not consistently pass the authenticated administrator. Reads/denials may save the entire mutable JSON store. No append-only/tamper-evident audit, distributed policy invalidation, writer fencing or atomic policy+audit durability is established. `JsonStore` caches the whole file and rewrites it; `AuthSystem` construction seeds the security catalog and saves. `ensureSecurityCatalog` can reassert built-in properties/membership links on startup. Do not adopt this persistence or policy lifecycle.
