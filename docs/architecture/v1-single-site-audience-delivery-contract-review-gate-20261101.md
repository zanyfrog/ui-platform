## Exact operator, reader and permission boundary

- **Owner:** one normally created disposable Application with its permanent registered Application ID, not an adopted copied manifest. A named authorized author saves eligible source; a principal with existing Application-scoped `ui.presentation.admin` explicitly publishes. Export permission (`ui.application.view`) is not a release grant.
- **Operation:** a separately named local operator, explicitly authorized in the next pilot decision, builds and starts/stops only the owned reader process. Manual host operation is governed by that authorization and OS access; it is not represented as an already integrated I-AM deployment permission. No grant is inferred from Application creation, a developer identity label or a free port.
- **Destination:** one agreed `http://127.0.0.1:<fixed-port>/`, root base `/`, with strict-port behavior. Port conflict must refuse; no automatic fallback, LAN binding, reverse tunnel or public exposure. This is a local demonstration using Vite's production-build preview facility, not production hosting qualification.
- **Reader:** local/operator-only means processes/users on the same machine can connect to loopback. It does **not** authenticate one OS user or exclude every other local process. If per-user reader authentication is required, this path does not enforce it and the pilot must stop for a different authorized access contract.
- **Separation:** the reader serves built site files only, without Builder, source roots, management/data/security APIs or dev refresh. It supplies no Builder credentials or grants. An already authenticated operator may independently retain Builder access; a separate port is not a browser-cookie or OS security boundary.

Important configuration condition: the Standard template enables a `/api` management proxy when `UI_PLATFORM_API_PORT` exists. Installed Vite's `resolvePreviewOptions` inherits `server.proxy`, and its preview middleware installs that proxy. The pilot must use a reviewed per-process environment with that variable absent and verify no effective reader proxy; do not inherit the Builder's launch environment blindly. Root/base variables and plugins must also match the approved reader configuration. If this cannot be established, **refuse host startup**, not relax separation. No environment was changed in this review.

Existing checks are defined in [v1-management-routes.ts](../../src/server/v1-management-routes.ts): Application creation `ui.platform.application.create`; Page read/edit `ui.page.view/edit` (administrative deletion `ui.page.admin`); composition/Shell/Menu read/edit `ui.presentation.view/edit`; Publish/rollback `ui.presentation.admin`; package management `ui.package.*` and Platform component administration remain separate. Development Preview requires `ui.application.edit` but is not the chosen reader host. Existing owner/session checks in [index.ts](../../src/server/index.ts) and protected security administration remain authoritative. The pilot requests no new capabilities or widened source reads.

## Release, asset and dependency identity

Use the **existing Application ID + active presentation version + captured composition membership** as source identity. Do not use only the draft presentation checksum: Page content has a separate composition fingerprint. `compositionSources` captures app.settings.json, shells, menus, styles, assets and src/pages; Publish also freezes referenced Platform Component closure under the version's composition directory. Validate all captured Pages, routes, default/selected Shells, Menu destinations and dependency closure through existing composition validation. Capture exactly three informational Pages and one shared Shell/Menu, with no custom executable functions, forms, reader data or Workflow/service actions. Trusted template/runtime/package code remains an explicit dependency, not a claim of zero executable JavaScript.

The build reads the published composition for Pages/Shells/Menus/CSS/assets and frozen Platform Components. It still resolves installed package implementations, application entry/config and helper code from build inputs outside that snapshot. Record their actual versions, lock/build configuration and physical input hashes; the version number alone does not pin them. A ZIP's version substitutions and copied dependencies are not a content seal or complete dependency-resolution proof.

For each release retain a diagnostic inventory of relative built-file paths/byte hashes, source version/fingerprint, dependency/build inputs and root base. This verifies the output artifact; it is **not** a new revision store or persistence authority. Reproducible input/byte provenance is required; bit-for-bit repeat-build determinism is unverified. Once built, imported local assets are inlined or emitted into that output. Later source asset edits should not affect the served output, but changing served files in place can. Verify asset bytes in the output inventory; disallow mutable remote asset/CSS/helper URLs for this pilot. Page-bundle equality alone proves neither dependencies nor image bytes.

## Smallest release/update/refusal contract

1. Complete and save source; drain admitted saves, validate the entire eligible composition and record its membership. Coordinate participating writers during capture. Existing mutation serialization does not exclude arbitrary external writers or prove multi-artifact atomicity; unexpected source/version/fingerprint changes refuse the candidate.
2. The authorized publisher explicitly invokes existing Presentation Publish. Verify its resulting active version and complete composition snapshot. Publish alone does not start or replace the reader host.
3. Build that selected published version using existing Application build scripts into a **new candidate output directory**, never the directory currently served. Record and verify all output and dependency identities. Build failure leaves the previous served output untouched. The Standard template requires Node >=22.12.0; the export wrapper's generic Node >=18 declaration is not sufficient runtime guidance for this template.
4. After candidate validation and separate explicit operator release, start existing Vite built-file serving for that candidate with the fixed loopback destination, reviewed no-proxy environment and strict port. Stable-port changes may require stopping the old owned process first: downtime is acceptable; atomic switching/zero downtime is not claimed. Do not kill unrelated processes to free the port.
5. Verify Home/About/Contact direct URLs, hard reload, shared Menu/content links, Back/Forward, decoded local images, computed CSS and unavailable routes. Standard main.ts matches composition routes and uses full Page navigation; Vite SPA fallback supplies index.html for direct URLs. Check correct displayed content, not merely HTTP 200. Built entry/assets must contain the declared release; record reader-observed bytes against the output inventory.
6. Ordinary Save and later unpublished edits must leave reader bytes/content unchanged. For one update, repeat explicit Publish → separate build → verified candidate → explicit operator stop/start at the same destination. Retain both complete outputs and their identities.
7. Invalid preparation refuses before changing the reader. If replacement startup/health fails, stop only that candidate and report unavailable; the operator may explicitly restart the previously retained complete output using the same existing command/config. This is manual restoration of a prior built directory, requiring verification—not an existing atomic deploy/rollback service. No automatic success claim after a failed restart.

Existing presentation rollback restores historical composition into **draft/source for review**, retains files absent from the historical snapshot and can report partial source operations. It is not an exact website rollback or live reader switch. Prefer the pilot's supported **safe-refusal contract**; validate any manual old-output restart separately. Do not add pointer swapping, migrations or a release manager to manufacture stronger guarantees.

The Standard template begins with Public/Admin Pages, two Shells/Menus and a referenced Platform Component. It is not the proposed three-Page/one-Shell/no-arbitrary-component site as created. The pilot must explicitly remove/replace only its own new placeholder content/references using existing controls and reference guards, or document a supported eligible template alternative. Default Shell/Region/Menu setup and Page creation controls exist; this exact reduction has not been demonstrated here. A template route named `/admin` is not an authentication boundary. Do not expose unintended routes just because their labels sound protected.
