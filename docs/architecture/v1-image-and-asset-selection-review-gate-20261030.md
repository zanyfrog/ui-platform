# V1 Page Builder — Image and Asset Selection Review Gate

2026-10-30. **Read-only existing-contract assessment. No implementation authorized or performed.** Guided Composed-Page Content Authoring is separately accepted and closed.

Recommend a small “Choose Application image” control in the existing managed HTML Image inspector. Reuse authorized Application asset listing/upload, preserve an Application-relative literal `src="assets/images/example.png"` and ordinary `alt`, and retain the current HTML-first Save/Reload and saved Design Preview contracts. No media registry, storage model or renderer is needed for the composed-Page workflow.

## Recommended minimal author workflow

1. Select a managed Image (`img`) within the Page-owned content Region, using existing insertion and Structure controls. Give the existing `img` insertion option a readable Image label if separately authorized.
2. Choose Application image. List only supported image paths returned by the authorized current-Application asset API, using a readable filename with path available to distinguish duplicate basenames. Empty, denied and failed listing states must be distinct; preserve the current source on cancellation or refusal.
3. Select an existing uploaded image, or use the existing Upload Application asset action if authorized. Refresh choices after successful upload; reuse its path, content-hash conflict check and explicit replacement confirmation. Do not create a second uploader or store.
4. Recheck the selected path's existence through asset info, retain the original Application/session ownership context, and update only the selected managed Image's literal HTML `src` with `setNodeAttribute`. Edit alternative text through the existing control. No asset ID or per-instance JSON authority is invented.
5. Save and Reload, then open Saved Design Preview and verify the rendered Application asset and retained Image identity/Region containment. Verify the admitted host only within its existing qualification. Image selection must not imply Publish or new route admission.

For the first increment, prefer composed Pages and existing Shell image editing where the saved Preview asset resolver is already supplied. Plain-Page support needs an explicit decision about the resolver gap below; do not silently offer a picker whose images will resolve against the Builder URL.

## Concrete gaps and bounded decisions

- **Image inspector connection is absent.** It exposes raw `src`/`alt` but does not request or select asset choices. Existing branding selection demonstrates the required API; the missing work is a small inspector control and context-safe async handling.
- **Permissions can prevent ordinary selection/upload.** Read and write require presentation permissions. Preserve existing denial and offer only actions admitted by the current user. No permission redesign belongs in this increment.
- **Plain-Page saved Preview resolver gap.** The current `preview.ts` plain branch calls `mountVisualArtifact(artifact, options)` without `assetUrl`; the composed branch supplies it. A plain Page's literal `assets/...` cannot be assumed to reach the Application asset API. Either bound the first increment to composed Pages/Shells or separately authorize wiring the existing resolver to eligible plain Page Preview. This is source-backed analysis, not a new browser failure demonstration.
- **Existence is not already a generic Image-save contract.** Ordinary `src` mutation validates URL syntax; the branding workspace checks asset existence, but generic HTML Image validation does not establish current asset existence. A picker should info-recheck selection, handle missing/stale assets, and specify behavior if the asset changes after selection. Do not promise content pinning or a multi-artifact transaction: image HTML stores a path, and asset bytes may change independently of the Page revision.
- **Listing is path/extension based, not decoded-image validation.** The API accepts bytes and serves extension-based MIME; it does not establish that an upload is a decodable image. Basename normalization can also produce names outside the stricter source grammar (for example multiple dots). Reuse normal refusal, expose a clear error, and verify decode failure behavior before claiming a reliable image workflow. No new format policy, SVG sanitizer or scanning subsystem is proposed here.
- **No deletion/reference registry is implied.** Existing path references do not establish incoming-image reference protection or an asset rename/delete lifecycle. Exclude those operations. Preserve branding-bound Shell images rather than silently converting an Application branding binding into a Page-specific source.
