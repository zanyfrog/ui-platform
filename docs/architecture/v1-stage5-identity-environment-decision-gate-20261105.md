## Minimum identity and session design for approval

1. Use the maintained ESM `openid-client` v6 line, pinned to an exact reviewed release/lockfile after approval. Its maintained version table and Code/PKCE support are documented in the [upstream repository](https://github.com/panva/openid-client). Do not implement custom JWT verification or install an unpinned `latest`. Discovery issuer is trusted configuration, never a query parameter; require HTTPS endpoints, expected issuer, client ID/audience, allowed signature algorithms and bounded JWKS refresh.
2. A login transaction has random state, nonce and PKCE verifier stored server-side with a five-minute one-use lifetime, bound to initiating browser, selected application, exact redirect URI and allowlisted local return path. Callback consumes it once; the library exchanges the code with S256 PKCE and validates signature, issuer, audience/authorized party, expiration and nonce. Bound clock tolerance, `iat`/`auth_time` and required MFA assurance must be configured and negatively tested. No implicit/password grant or wildcard callbacks. ID/access/refresh tokens never enter browser storage, URLs, application logs or public release files.
3. Store a permanent enrollment record with a unique `(exact issuer, opaque subject)` key pointing to the permanent I-AM User ID, active/approved status, enrollment revision and audit identity. Case/Unicode/email normalization must never merge subjects. Client-specific subjects may have multiple separately approved links to one User, each proved by a validated provider login and trusted operator approval. Unknown, duplicate, disabled or unapproved mappings fail closed; callback cannot create a privileged User or assignment. Invitation acceptance can establish a pending identity only; an independent approver binds it to the intended User. Email and provider roles/groups/profile are informational. Existing I-AM WP3 remains the only source of role assignments, grant ceilings and last-administrator rules.
4. A random 256-bit opaque session identifier is issued only after approved mapping and active I-AM User checks. Store only its digest server-side; bind session to app/client/audience, User, enrollment revision and revocation epoch. Use `__Host-` cookie, Secure, HttpOnly, SameSite=Lax, Path=/, no Domain. Separate management origin/cookie/client. Proposed limits: 30-minute idle, eight-hour absolute lifetime, fresh MFA within 15 minutes for sensitive administration. Rotate after login/reauthentication and identity changes; delete old session atomically. App switching requires that application's approved session and current I-AM authorization.
5. Every protected operation rechecks active User, enrollment and session epoch and evaluates current I-AM/resource ownership. Mutations require server-bound CSRF token and exact configured Origin; reject missing/null/foreign origins and caller actor/admin headers. Reads use safe methods with no side effects. Logout is a CSRF-protected POST that revokes local state and clears the cookie; optional provider logout uses a fixed allowlisted return URL. No automatic write retries on login/service failure.
6. Simplest restart rule: session store is process-owned/ephemeral and restart invalidates all sessions and pending login transactions. Persist identity mappings/approval/revocation epochs independently. Do not restore sessions from backups. Retaining sessions across restart would require a separately reviewed durable session design. No refresh tokens initially; require interactive reauthentication at session expiry.
7. Immediate local disable/revoke must deny the next protected request, including in an open browser. Provider-side block alone is insufficient. Proposed operator procedure disables local mapping/User and bumps session epoch first, then blocks provider login. Provider-only lifecycle events must be authenticated, replay-protected and reconciled; until qualified, provider-only immediate revocation remains BLOCKED, not implied by logout or short token lifetimes. A chosen propagation bound/outage policy must be approved before P1/P2 acceptance.
8. Proposed internal trust: runtime and management have separate narrowly scoped client certificates; Data Services requires mTLS plus short-lived, one-use asymmetric signed actor assertions. Bind issuer/service, exact Data audience, application, User, session/enrollment epoch, release identity, request method/path/body digest, issue/expiry (at most 15 seconds) and random replay ID. Reject unknown keys, wrong app/audience, future/expired/replayed assertions and all development token formats. Never forward browser authorization or actor headers. Certificate/service identity alone grants no User or Dataset permission. Data Services creates opaque trusted handles and independently checks I-AM, applied schema and delegation at execution. Restart invalidates replay state by rotating the receiving instance audience/epoch. This is a proposed P2 adapter, not a replacement of I-AM or an implemented protocol.

## Proposed single-host topology and storage

Ubuntu 24.04 LTS is a conservative supported candidate; [Canonical support schedule](https://ubuntu.com/about/release-cycle). Use a patched, pinned Node 24 LTS runtime after isolated compatibility checks, especially `node:sqlite`, Linux case sensitivity, package admission and compiled deployment paths. The repository's `>=18` engine declaration is insufficient; [Node's release table](https://nodejs.org/en/about/previous-releases) lists supported LTS lines. No claim that a Linux target has been tested.

| Deployment/recovery / separate operator identity | No browser-facing listener. Stage 6/7 authorization required. | Own final immutable release creation/selection and coordinated recovery. Runtime cannot replace release pointer/files. Backup operator gets explicit temporary access across stores under quiescence, not a standing runtime admin role. |

Use fixed nonlogin users and owner/group permissions, `UMask=0077`, systemd `NoNewPrivileges`, `ProtectSystem=strict`, explicit `ReadWritePaths`, `InaccessiblePaths`, protected home/devices and bounded capabilities, verified on the actual OS. Read-only mounts alone do not prevent reading sensitive roots: explicit denial/permissions matter. Unix/loopback connectivity does not authenticate a caller. [systemd execution isolation](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html), [Caddy TLS behavior](https://caddyserver.com/docs/automatic-https).

Suggested roots are explicit separate directories for authoring, selected immutable releases, policy/mapping state, applied schema/registry, records, private assets, and append-only audit collection. Public release manifests use an allowlist of public resources; merely putting private files in a subfolder named private is insufficient. No public web server root can contain authoring, private assets, secrets or backup generations. Keep SQLite/WAL and JSON/file stores on supported local storage, not independently replicated/network-mounted files. One physical server remains a single failure domain.

## Stage 7 design constraints, without backup execution

One backup generation must cover application/Component definitions, immutable releases and selection, schema publications/applied state/ownership registry, ORM records, public/private asset versions, I-AM authority/mapping/revocation state, deployment configuration and referenced package/key identifiers. SQLite WAL cannot be omitted or copied independently while writers run. Plan coordinated writer admission stop, drain in-flight operations/jobs/uploads/policy activation/publication, acquire acknowledgements from every service/worker, checkpoint or use an approved consistent SQLite capture, capture one manifest with revisions/hashes, then release writers. An unresponsive writer means no usable generation; do not mark a partial capture successful. Implementation must preserve this coordination seam.

Encrypt complete generations and verify off-server storage with separately held restore/decryption access. Runtime and management cannot possess deletion/retention keys. Keep recovery key custody outside the sole server with a separately authorized operator and tested access plan; internal signing/session keys must be rotated/re-enrolled after restore. Never restore old live sessions or blindly reactivate old assignments: reconcile later revocations and environment identity before admitting traffic. Audit retention/collector is separate from rolling backups so restoring data cannot erase newer security history. Design for 30-day backup and 90-day audit retention; proposed four-hour captures need transfer/retry/alert margin to keep newest verified restore point within six hours. No schedule constitutes RPO evidence. Maintenance window, dataset size, destination, encryption system, operators and RTO are still unknown. No operational backup, retention test or restore executed here.
