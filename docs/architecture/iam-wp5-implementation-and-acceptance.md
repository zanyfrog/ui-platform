## Implemented enforcement contract

`SecuredDatasetOperationEngine` depends on the exported WP4 planner and owner registry contracts, not raw I-AM tables. The trusted host supplies an opaque identity context, matching actor, application and authority. HTTP JSON supplies Dataset intent only; a client-provided actor, policy, plan, application or context is rejected. The host must provide an authenticator to `createSecuredOperationRequestHandler`; no WP7 production authentication was invented.

The engine resolves a permanent Dataset ID through the applied owner binding, plans and asserts current authority before protected ORM access, and rechecks exact request/owner/policy freshness. READ compiles only safe positive candidate predicates for the ORM, loads required physical Fields, and applies exact per-row/per-Field ALLOW and DENY checks inside DOE. It evaluates user filters and sorts only where their Field usage is authorized, then paginates. COUNT and EXISTS use post-security rows. Unsupported group, aggregate, join, computed and export requests fail closed. Hidden properties are omitted; authorized `null` remains present.

CREATE, UPDATE and DELETE obtain a provisional plan before controlled old-state reads. UPDATE evaluates old and full new state; DELETE evaluates old state. Defaults and before Trigger mutations are included in a final plan for every batch item and touched Field. The plan is rechecked before ORM write and again before root commit. Mixed unauthorized batches rollback; filter/partial-write and non-atomic options reject. Write results report counts and commit outcome without returning records, because WRITE does not imply READ. Trigger children run under the current actor and share the root transaction before commit. A child failure poisons the root; unknown commit and post-commit failure remain distinct. Full old snapshots remain internal to DOE; a separate current-actor READ plan projects only authorized old-state Fields for UPDATE/DELETE Triggers. The user approved this rule during WP5.

`createSecuredOperationRequestHandler` exposes only protected `/queries` and `/operations`. `secured-service.ts` now composes the deployed development-only host from a server-controlled manifest: one fixed bearer token maps to one fixed User, application and authority. The User must exist and be active in the current WP1 authority snapshot. A replaceable `TrustedActorProvider` creates opaque contexts, verifies them for WP2, and attests WP4 requests. The host composes the verified applied owner registry, qualified schema resolver, WP2 evaluator, WP4 planner, trigger registry and DOE over the ORM. Missing/invalid configuration, disabled feature and production mode fail startup; missing/invalid token, unknown/inactive User, I-AM failure and resource-authority failure fail requests before protected ORM writes. The UI editor development session is never an actor source. The earlier request handler and manager remain for isolated legacy activation/compatibility tests. The standalone legacy service requires `UI_PLATFORM_ALLOW_LEGACY_DEV_OPERATIONS=1` and rejects `NODE_ENV=production`. UI Platform no longer declares a direct root `@ui-platform/orm` dependency, and a boundary test rejects ORM imports from ordinary `src` application code. Approved owner-controlled infrastructure still uses ORM directly where needed.

The shared `ApplicationDataClient` in `@uib/platform-core/application-data` expresses READ, COUNT, EXISTS, CREATE, UPDATE and DELETE using the existing DOE intent contracts. Its HTTP transport sends intent to the UI Platform host's `/api/application-data/{queries,operations}` routes. That host forwards only the bearer credential and unchanged Dataset intent to the existing protected DOE HTTP host, configured by `UI_PLATFORM_WP5_DATASET_HOST_URL`; it does not create an actor, interpret policy, or fall back to ORM. The protected host's `TrustedActorProvider` establishes the actor. These routes are development-only and require explicit `UI_PLATFORM_WP5_APPLICATION_DATA=1`; missing backend configuration, missing credentials and production mode fail closed. The UI editor session has no DOE authority.

`bindDatasetForm` attaches to the existing `uib-forms-form-submit` event and calls the same `ApplicationDataClient` with an explicit Dataset operation. It preserves all event values, including hidden controls, and returns the DOE result or error to the application callback. Form validity remains a separate client-side check; a valid Form can still be denied by DOE. There is no checked-in full application Page Dataset runtime: UI Platform can edit Page source, while the configured `apps` directory is empty and `templates` is absent. Page/Component code can import the shared client directly; the end-to-end test uses that path for a protected READ. This is the minimum common data boundary, not a Page framework.

## Compatibility, limitations and pending decisions

The development host is an opt-in protected deployment target, with its identity manifest held server-side. Existing v0.1 clients using the legacy JSON-actor HTTP route cannot be silently treated as authenticated WP5 clients. The default standalone legacy executable remains closed. The development bearer token is a temporary fixed-User credential supplied by the application caller; it is not WP7 production authentication. Application authors must bind a Form's event to an explicit Dataset operation; Form submission is not synonymous with CREATE. No complete checked-in Page runtime or generic Page data-binding framework exists; Page and Component consumers use the exported shared client directly.

The protected Trigger path exposes only separately READ-authorized old-state Fields and withholds old-only merged new Fields from current-actor handlers. This is an intentional compatibility restriction for existing Triggers that expected full old rows. They need an explicit READ grant to see old Fields; WP6 delegated Service execution is not implemented.

The existing JSON ORM persists datasets sequentially at commit. A pre-commit rejection discards staging, but a failure during a multi-dataset commit has an **unknown** outcome and cannot be called transaction-wide atomic. Complete multi-host isolation, production sessions/immediate distributed revocation, durable application-data audit, advanced aggregate disclosure controls, Blueprint orchestration and production cutover remain outside this pass. Aggregate/group/export are unavailable on the protected path until their full capability and result contracts exist. The host must ensure that its reported actor matches the opaque attested context; DOE never accepts actor identity from HTTP JSON.
