## C1 — Trusted service contract and protected admission

The existing reference notification implementation is shared by the legacy reference fixture and normal host through `src/server/automation-services.ts`. It clones an input into one host's in-memory sink and returns `{delivered:true}`. That means memory append, not durable/external notification delivery. The legacy reference fixture deliberately projects its old callback-only interface; its privileged fixture setup is not normal-host onboarding or approval.

The normal host opts into `automation.services: ['reference.notification']` in its trusted deployment config. New WP3 development deployments include that registration; older deployments without it retain an empty service catalog. Unknown or duplicate registrations fail startup. Registration never grants a permission. Approved Workflow IDs and their existing invocation permission remain separate host configuration. No user-authored callback, public registration endpoint, additional automation runtime or Application source format was introduced.

`src/shared/automation-service-contract.ts` owns the approved fixed version-1 contract: exactly `{message:string}`, 1–2000 UTF-16 code units, and exactly `{delivered:true}`. Unknown keys, coercion, missing paths and wrong types are rejected. Nested descriptor metadata is frozen; its digest covers identity, version, I/O metadata, phase restrictions, permission and implementation binding. The runtime rechecks the descriptor/current map entry at admission; incompatible contracts do not silently replace version 1. This finite callback contract does not replace Dataset schema validation or native action/value validators.

The dedicated permission is `automation.reference.notification.invoke`. The service resolves as an active Application-qualified `artifact` under its Application using the existing resource authority, with no new resource kind or service principal. Explicit I-AM permission definitions, scoped grants and activation are prerequisites. Dataset write, Workflow editing or a registered string does not confer invocation authority. The host creates no automatic creator/fixture administrator grant.

Data Services' existing secured host exposes a host-only `invokeAuthorized` port. It attests the original opaque identity, checks authority/Application/resource/permission through `SecurityAuthorizationEvaluator`, rejects conditional or denied decisions, and calls `assertCurrent` immediately before invoking the effect. The engine carries a bounded service-invocation closure into TriggerContext; it closes with the operation and cannot be recreated from actor JSON or declarative values. Workflows use the same engine boundary with their existing `TrustedDatasetExecution`. Native published service programs retain their existing publication, digest, service-use approval, execution capability and permission-ceiling path.

The normal runtime is strict: only the approved descriptor is usable, only the pinned applied Dataset/primary key is supported, and a nontransactional service is allowed in a Workflow or Trigger afterCommit. Disabled drafts remain repairable without executing or poisoning enabled definitions. Other Dataset actions fail with `MULTI_DATASET_AUTOMATION_UNSUPPORTED`; they are never remapped. Existing protected reads/writes, mandatory validation, inherited authority and native Trigger Registry ordering remain authoritative.

## C2–C3 — Typed authoring over native definitions

The existing automation editor retains its WP2 `EditingLifecycle`, source transports, two-second autosave, Save Now, Undo/Redo, conflict/reload, suspended access and recovery. Normal creation chooses a registered Application and applied Dataset through the protected catalog and resolves the primary key/physical binding through the host. Permanent definition and action IDs remain native; moving actions does not regenerate them. Creation rechecks the existing captured management authority before writing source; a refused new artifact leaves no source or unintended link. Creation/type/list/save controls are guarded while their management operation is in flight, preventing a displayed type from diverging from the active endpoint.

The new `src/client/automation/authoring-controls.ts` implements only controls for native ordered set/reject/CRUD/service actions, native Trigger phase/priority/each-or-batch scope and existing AutomationValue literals, explicit record/oldRecord/newRecord/context paths and named fields. It adds no interpolation, operators, prior-step variable source or executable text. Structured CRUD records/query use those same named-field values. Unsupported saved literals/targets remain visible with diagnostics instead of being silently rewritten. Native save and runtime validation remain authoritative.

Service selection comes from the approved host registration and current dedicated invocation authority. Workflow selection is independently filtered by its existing invocation permission. Applied permanent Field IDs and physical keys are returned by the existing applied resource binding. The catalog is read-only metadata, not a new persistence authority. Applied Dataset metadata separately requires the existing `ui.artifact.view` permission on the Application datasets artifact; service and Workflow permissions cannot substitute for that view authority. The advanced source repair surface remains available and is not used for primary WP5-C browser acceptance.

## C4 — Native invocation and honest inspection

WP5-B instance-event controls now expose the existing Visual `workflow` action. They select an authorized permanent Workflow ID, existing scalar record expression and explicit declared result state. They modify the Page instance, not shared Form/package definitions. The shared renderer still invokes protected `workflow.run` through the existing ApplicationDataClient services and native Workflow endpoint.

Form `submitSucceeded` emits the protected write result wrapped in `{result}`; it does not promise a new primary-record ID. The verified edit journey uses existing `route.id` for the route-selected record. `recordCreated`/`recordUpdated` keep their saved-record payload semantics. No Form event schema was changed to invent an ID.

Workflow results retain native success/execution IDs/completedSteps/failedStep/committedSteps and postCommit failure/duplicate-write semantics. Additive `failedActionId` correlates the failed native step to its stable action ID; `serviceEffects` distinguishes `not-performed`, `occurred` and `unknown`. Dataset commit counters never count a memory notification as a Dataset write. A later denial or service/output failure does not roll back earlier committed writes. Invalid output after a possible effect is unknown unless trusted evidence establishes otherwise. A trusted deterministic test substitute can report a fail-before-effect outcome; no source input can assert that evidence.

The existing Workflow transport preserves confirmed request-denial outcomes separately from server/transport uncertainty. The renderer stores the honest result in the declared local state and exposes its paths through existing binding controls. Neither transport failure nor afterCommit failure triggers an automatic retry. Design preview has no executable Workflow capability and cannot append notifications or persist records; missing capability is displayed as unavailable.

## C5 — Verification scope and retained prerequisites

See [verification, attempts and inventory](builder-v1-wp5-c-verification.md). The browser fixture authors the Trigger/Workflow and Page/Form invocation metadata using normal Builder controls. It uses a separately disclosed trusted Workflow allowlist deployment after UI allocation of the permanent ID. That existing host prerequisite is not proof of UI-only host approval or Application provisioning. Security setup uses existing audited I-AM activation; it does not bypass service permissions.

The runtime fixture's independent notification sink and temporary protected Dataset storage cannot affect another host's sink or ordinary production storage. Normal references are not reused as test-service singletons; failure and transport substitutes are trusted test assembly only. General isolated test-session UI/infrastructure remains WP5-G. There is no durable notification queue, audit product or retry facility.

Final evidence is 446/446 UI tests (63 files), 760/760 Data Services tests, 146/146 editor/storage contracts, successful builds/typechecks/production exclusion and actual browser proof. The full UI gate ran serially with explicit 30-second default test/hook limits and one configured retry; this is not a claim that every case passed its first attempt.

The first parallel full UI run encountered competing source writers and transitional legacy-test expectations. Failed attempts remain evidence. Serial regression execution avoids tests sharing global source fixtures; it is not a source-lock remediation or simultaneous-use proof. D6 admission/locking planning and remediation remain WP5-F under separate review, with reliable simultaneous Builder/runtime operation required before WP5-I acceptance. Full management-restart/browser evidence remains A37 in WP6.

All 351 historical and 157 WP5-B evidence files and their original hashes were verified byte-identical after restoring raw fixture outputs. Three earlier planning evidence files are also unchanged. All 40 umbrella requirements remain unchecked. **No WP5-D implementation is included or authorized by this record.**
