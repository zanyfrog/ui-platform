# WP5-F Production Preview Integration Readiness

2026-10-24. **Source/documentation-only decision review.** Accepted L1-A/B, L2-A/B and L3-A/B provide bounded contracts, models and native compatibility; they do not compose into an authorized production Preview by themselves. [L3-B closure](builder-v1-wp5-f-l3b-closure-20261024.md) records its limited acceptance separately. Complete WP5-F, D6 and WP5-I remain open and unaccepted; all 40 umbrella requirements remain unchecked.

## Decision

Do not activate saved rendering yet. Recommend **one production-interface increment: Builder Saved Preview Request and Readiness Wiring**, with no capture provider or render-success branch. It connects the actual production Builder selection/lifecycle to an explicit saved-Preview request boundary and truthful unavailable result. It creates no further pure model, synthetic renderer or substitute saved content. It is independently shippable UI/request plumbing, not delivery of the saved Card vertical slice.

If a next increment must display actual saved content, none is safely authorizable without first resolving coherent protected acquisition, real source-instance identity and trusted authority/delivery prerequisites in the consolidated matrix. A successful fixture/native/model run cannot bypass them. The proposed seam advances real integration while those gates remain closed; its acceptance must not be described as saved rendering.

## 2. First actual saved Card vertical slice

The minimum honest content target is **one explicitly identified canonical Card instance in an authorized saved Application-owned Page revision**, isolated from unsupported composition. Selecting the installed Card package Definition alone does not identify a saved instance. Builder currently identifies an artifact; node focus/settings are not carried through the shared Preview binding. A future selection contract must include original Application/owner-qualified Page identity, saved native revision and stable saved node identity, alongside the canonical Card/package identity. The label must name the source Page/node and saved revision; never relabel authored sample data as that saved content.

Initial supported source subset should be decided explicitly: actual canonical `data-uip-component`/`data-uip-settings` reference, supported literal settings, no dynamic binding/function/service/event/onLoad, arbitrary children, CSS/resource or composition dependency needed to reproduce that isolated instance. If a Shell/theme or other context affects semantics, either capture/admit it or return unavailable; do not approximate. Native source parsing/validation must establish this from captured saved bytes, not the editor's dirty DOM or a guessed default Card.

Required transitions:

1. **Builder selection → request:** derive original artifact/owner/Application/session and explicit saved-instance target; carry dirty as warning only. Missing/ambiguous node or repair-only identity is unavailable. Opening/Refresh must not save/flush/reload/discard or alter autosave/history.
2. **Request → authorized acquisition:** real server rebinds original subject/session and permanent owner, checks all required source/field visibility and enters existing D6 graph/role admission. It must distinguish busy/unresolved/recovery/denied/stale, not retry an admitted callback. Current authorize response is editor/discovery data, not a Preview capability or coherent immutable capture.
3. **Acquisition → immutable capture:** resolve selected node/Definition/package activation and complete needed byte/membership closure, validate and recheck all participants/current owner/authority. Reject entire changed/missing/ambiguous/unsupported closure. Produce exact canonical bytes/index with content identity and a separate original-bound authority envelope.
4. **Capture → native admission:** map real saved Page/node identity to L3's canonical Card identity **without losing either**. Current L3 binding.selectedIdentity is the package Card ID; L1/L2 carry opaque source identities. A production envelope must bind source artifact/node/revision and implementation Card/package/Definition together. Existing model types are concepts, not an already compatible production wire protocol.
5. **Admission → display:** only current, healthy, unexpired admitted capture may use approved fixed native bundle; every resource delivery freshly checks original authority and immutable index. No live module/source URL or ordinary service fallback. Current L3 frame's supplied allow/time context is insufficient for this production decision.
6. **Display → Refresh/invalidation/disposal:** source change marks static stale/inert, explicit Refresh makes a new candidate; observed authority change or uncertain health hides before awaiting cleanup. Permanent owner/session switch, expiry, gaps, channel failure and disposal prevent late resurrection. Reauthorization requires reconciliation and explicit Refresh. Future server access termination and browser lifecycle must both be evidenced; local simulation is insufficient.

## 4. Prioritized integration sequence

1. Implement only the request/readiness seam proposed below, if authorized. This closes actual Builder identity/lifecycle/request plumbing without pretending data or authority exists.
2. Decide the source Page/node envelope and exact literal native subset; complete deployed source-writer/root and authority writer/history/session/owner design. These are independent source/design tracks, not another pure model or renderer.
3. Resolve the D6 operational qualification boundary with separately authorized evidence and any independently justified operational decision. Windows Identity/N01/token/elevation/VM/WinPE/Foundation recovery stay paused unless separately justified and authorized; none is a shortcut required by the proposed seam.
4. Implement/qualify real authority invalidation, immutable delivery and source acquisition under exact separate backend/protected execution gates. Agree timing/resource ceilings and disclosure-race semantics before display activation. No one lane's pass accepts the others.
5. Bind those providers to the production request seam and admitted Card path for the one saved Page/node subset; verify real capture, concurrent changes, actual denied/revoked delivery, browser isolation, lifecycle and ordinary editing/runtime preservation. Then review that slice explicitly; complete F/G/H/I remain separate decisions.
