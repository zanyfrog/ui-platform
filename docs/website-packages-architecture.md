# Website Packages Architecture

## Purpose

This document defines the package architecture for building the Modular web site as a set of small, composable packages. The goal is to separate content, design primitives, site-specific composition, and deployment concerns so the web site can grow without turning into a single tightly coupled application.

## Guiding Principles

- Keep package ownership clear: each package should have one primary reason to change.
- Reuse existing Modular UI primitives before introducing site-only components.
- Keep content portable and reviewable in markdown or structured data.
- Keep framework-specific code at the site shell boundary.
- Make package APIs boring: explicit exports, typed configuration, and stable entry points.
- Prefer incremental migration: new packages should be useful before the whole site depends on them.

## Proposed Package Map

### `@modular/site`

The runnable web site application.

Responsibilities:

- Own routing, rendering mode, metadata, analytics wiring, and deployment configuration.
- Compose page templates from content and web components.
- Provide the production build target.
- Import from the website packages rather than owning reusable UI or content logic directly.

Non-responsibilities:

- Defining shared design tokens.
- Owning reusable web components.
- Containing long-form source content as implementation code.

Suggested location:

```text
apps/site
```

### `@modular/site-content`

The content source package for the web site.

Responsibilities:

- Store markdown, MDX, or structured content for pages, docs, examples, release notes, and marketing copy.
- Define content schemas and validation rules.
- Export typed content collections to the site app.
- Keep author-facing content separate from rendering components.

Suggested location:

```text
packages/site-content
```

Initial exports:

```ts
export { getPage, listPages } from "./pages";
export { getDocsEntry, listDocsEntries } from "./docs";
export { getExample, listExamples } from "./examples";
```

### `@modular/site-ui`

The site composition layer.

Responsibilities:

- Provide site-specific page sections, layouts, navigation, footers, calls to action, and content renderers.
- Compose lower-level Modular UI components into website-ready patterns.
- Keep visual decisions close to the site while avoiding duplication inside route files.

Non-responsibilities:

- Replacing shared UI primitives.
- Owning global design tokens.
- Fetching or validating content.

Suggested location:

```text
packages/site-ui
```

Initial exports:

```ts
export { SiteHeader } from "./components/site-header";
export { SiteFooter } from "./components/site-footer";
export { MarkdownPage } from "./components/markdown-page";
export { DocsShell } from "./components/docs-shell";
```

### `@modular/site-theme`

The website theme bridge.

Responsibilities:

- Map existing Modular design tokens into the web site theme.
- Export CSS custom properties, typography rules, color modes, spacing aliases, and surface conventions.
- Provide a stable contract between shared UI packages and the site app.

Suggested location:

```text
packages/site-theme
```

Initial exports:

```ts
export { siteTheme } from "./theme";
export "./styles.css";
```

### `@modular/site-assets`

The shared asset package for website media.

Responsibilities:

- Own optimized images, icons, Open Graph assets, favicons, and downloadable static files.
- Provide named asset imports where the bundler supports them.
- Keep generated or large assets out of route implementation code.

Suggested location:

```text
packages/site-assets
```

### `@modular/site-config`

The typed configuration package for website-level constants.

Responsibilities:

- Own nav structure, footer links, social links, canonical URLs, feature flags, and content collection configuration.
- Export data as typed modules.
- Avoid direct framework runtime dependencies.

Suggested location:

```text
packages/site-config
```

Initial exports:

```ts
export { siteConfig } from "./site-config";
export { mainNav, footerNav } from "./navigation";
```

## Dependency Direction

Dependencies should point inward from the runnable app toward reusable packages:

```text
@modular/site
  -> @modular/site-ui
  -> @modular/site-theme
  -> existing Modular UI packages

@modular/site
  -> @modular/site-content
  -> @modular/site-config

@modular/site
  -> @modular/site-assets

@modular/site-ui
  -> @modular/site-config
  -> @modular/site-theme
```

Rules:

- `@modular/site` can depend on all website packages.
- `@modular/site-ui` can depend on shared UI packages, `site-theme`, and `site-config`.
- `@modular/site-content` can depend on `site-config` for collection names and URL rules.
- `site-content` should not depend on `site-ui` or the site app.
- `site-theme`, `site-config`, and `site-assets` should stay framework-light.

## Markdown Content Model

Use markdown as the durable authoring layer. Each content type should have frontmatter plus body content.

Example page:

```md
---
title: "Components"
description: "Composable primitives for building Modular interfaces."
slug: "/components"
status: "published"
---

# Components

Content goes here.
```

Recommended content collections:

- `pages`: top-level editorial and product pages.
- `docs`: documentation entries with sidebar ordering.
- `examples`: runnable or embedded UI examples.
- `changelog`: release notes and migration notes.
- `case-studies`: optional customer or project stories.

Recommended frontmatter fields:

```ts
type BaseContentMeta = {
  title: string;
  description: string;
  slug: string;
  status: "draft" | "published" | "archived";
  order?: number;
  tags?: string[];
};
```

## Package Creation Checklist

For each new package:

- Create `package.json` with the correct workspace name.
- Add `README.md` explaining purpose, public exports, and ownership.
- Add `src/index.ts` as the public API.
- Add TypeScript configuration using the repo's existing package pattern.
- Add build, lint, typecheck, and test scripts only where the package needs them.
- Add exports to the workspace tooling only after the package has a real consumer.
- Add one small integration from `@modular/site` to prove the dependency path.

## First Implementation Slice

Start with the smallest slice that creates useful architecture without overbuilding:

1. Create `apps/site` as the runnable web site shell.
2. Create `packages/site-config` with navigation and site metadata.
3. Create `packages/site-content` with one markdown page and a typed loader.
4. Create `packages/site-theme` with website CSS variables mapped to existing Modular tokens.
5. Create `packages/site-ui` with header, footer, and markdown page composition.
6. Wire `apps/site` to render the first markdown-backed page.

This slice proves routing, content loading, package exports, styling, and composition before adding docs, examples, search, or deployment complexity.

## Open Decisions

- Which app framework should own `apps/site` if the repo does not already standardize on one?
- Should markdown rendering use plain markdown, MDX, or a content collection tool?
- Should documentation and marketing pages share one renderer or have separate page templates?
- Which existing Modular UI packages are stable enough for public website composition?
- What should be generated at build time versus loaded dynamically?
